# Native AOT Compatibility Research

Status: research only — no ADR, no implementation plan. This document exists to ground a future ADR in evidence from the actual codebase and current Microsoft/AWS guidance.

Date: 2026-09-08

## 1. Executive summary

AlexaVoxCraft cannot honestly claim Native AOT compatibility today, and the gap is narrower and more tractable than the size of the codebase suggests. The library already multi-targets `net8.0;net9.0;net10.0;net11.0` (`src/Directory.Build.props:5`), already has a working precedent for eliminating runtime reflection in a different subsystem (the C#-interceptor-based MediatR DI source generator, `src/AlexaVoxCraft.MediatR.Generators`), and its JSON polymorphism is already implemented as **closed, compile-time-enumerable discriminator tables** (`typeof(X)` literals in `ConcurrentDictionary<string,Type>`/`IDictionary<string,Type>`) rather than open-ended runtime type discovery. That is the single most important finding in this research: the *shape* of AlexaVoxCraft's polymorphic converters (`RequestConverter`, `BasePolymorphicConverter<T>`, `APLComponentConverter`, and friends) is already compatible with a source-generated `JsonSerializerContext`, because they all resolve to a statically-known, finite set of CLR types and call the non-generic `JsonSerializer.Deserialize(json, Type, JsonSerializerOptions)` overload, which a generated context services correctly for any type it declares via `[JsonSerializable]`.

The actual blocker is concentrated in one place: `AlexaJsonOptions.CreateOptions()` (`src/AlexaVoxCraft.Model/Serialization/AlexaJsonOptions.cs:50-77`) builds the **single, process-wide `JsonSerializerOptions`** used by nearly the entire library — Model, Model.Apl, MediatR, MediatR.Lambda, MinimalLambda, Lambda — on top of `AlexaTypeResolver : DefaultJsonTypeInfoResolver` (`src/AlexaVoxCraft.Model/Serialization/AlexaTypeResolver.cs:8`). `DefaultJsonTypeInfoResolver` is System.Text.Json's fully reflection-based metadata resolver — the exact type Microsoft's own trimming/AOT guidance identifies as incompatible with `PublishTrimmed`/`PublishAot` once `JsonSerializerIsReflectionEnabledByDefault` is turned off (which happens automatically under those publish modes unless overridden). Every JSON operation in the library — request deserialization, response serialization, APL document assembly, session/persistent attribute storage (`JsonAttributeBag`), SMAPI/ISP HTTP clients — ultimately funnels through this one reflection-based resolver, either via `AlexaJsonOptions.DefaultOptions` directly or via independently-constructed `new JsonSerializerOptions { ... }` instances that have no `TypeInfoResolver` set at all (`src/AlexaVoxCraft.Http/Clients/BaseClient.cs:36-41`, `src/AlexaVoxCraft.Smapi/Clients/AlexaSkillInvocationClient.cs:22`) and therefore fall back to the same reflection default.

A second, independent hazard exists outside JSON entirely: `SkillMediator.Send` dispatches to handlers via `Activator.CreateInstance(typeof(RequestHandlerWrapperImpl<>).MakeGenericType(t))` where `t = request.Request.GetType()` is a runtime value (`src/AlexaVoxCraft.MediatR/SkillMediator.cs:58-60`). This is the canonical "MediatR-style mediator" reflection pattern and is a distinct AOT/trim concern from the JSON one, even though in practice it operates over a closed, small set of reference types. **This is treated as a hard gate, not an optional follow-on**: Native AOT support is a product-level capability claim — "AlexaVoxCraft supports Native AOT" is a statement about whether a consumer's skill runs end-to-end under `PublishAot`, not merely whether its JSON serializes correctly — so this hazard must be resolved and validated (§11) before any release is labeled Native AOT compatible, regardless of whether the fix ships in the same PR as the JSON work or as a separately sequenced workstream (§13 step 8).

There *is* a previous, narrow attempt at AOT-flavored work in the codebase: `JsonStringEnumConverterWithEnumMemberAttrSupport<TEnum>` (`src/AlexaVoxCraft.Model/Response/Converters/JsonStringEnumConverterWithEnumMemberAttrSupport.cs`) carries a `[DynamicallyAccessedMembers(DynamicallyAccessedMemberTypes.PublicFields)]` annotation on its generic `TEnum` parameter, and a larger, commented-out alternative design (lines 7-41 of the same file) shows an earlier, abandoned attempt to build the enum converter on top of STJ's own `JsonStringEnumConverter<TEnum>` with a custom `JsonNamingPolicy`. Neither of these constitutes a real "Native AOT initiative" — there is no `JsonSerializerContext`, no `[JsonSerializable]`, no `IsAotCompatible`/`IsTrimmable` MSBuild property, and no `PublishAot` usage anywhere in the repository (confirmed by full-repo grep, and by git history search across all branches). The enum-converter annotation is best read as a single engineer's defensive, half-finished gesture toward trim-safety on one narrow surface (enum parsing), not a project-wide architectural decision, and it does not by itself make anything AOT-compatible because the `JsonSerializerOptions` that carries this converter is itself irreducibly reflection-based.

**Bottom line recommendation** (elaborated in §12-13): AlexaVoxCraft should ship one or more library-owned, **internal** `JsonSerializerContext` classes (one per package that owns closed model types: `AlexaVoxCraft.Model`, `AlexaVoxCraft.Model.Apl`, `AlexaVoxCraft.Model.InSkillPurchasing`, `AlexaVoxCraft.Smapi`), rebuild `AlexaJsonOptions.CreateOptions()`'s default `TypeInfoResolver` on top of them (combined via `JsonTypeInfoResolver.Combine(...)`, with `AlexaJsonOptions.RegisterTypeModifier<T>` re-expressed via `JsonTypeInfoResolver.WithAddedModifier(...)` so it keeps working unchanged — proven mechanism, §7), and add exactly one new public method, `AlexaJsonOptions.RegisterTypeInfoResolver(IJsonTypeInfoResolver)`, so a consumer's own generated context (for `JsonAttributeBag`/`BaseClient` custom types, or a custom `IDirective`/`IRequestTypeResolver` registered via the existing `RegisterDirectiveDerivedType<T>`/`RegisterRequestTypeResolver<T>` APIs) can be appended to the chain. Nothing about AlexaVoxCraft's own `JsonSerializerContext` types needs to be public — the resolver-chain method is the entire consumer-facing surface. **Scope correction from the prior pass**: per explicit product-owner clarification, AlexaVoxCraft.Smapi is not tooling-only — SMAPI clients (`AlexaSkillInvocationClient`, `AlexaInteractionModelClient`) are also invoked from application code running inside Lambda functions in real AlexaVoxCraft-based skills, a usage this repo's internal `ProjectReference` graph cannot show because it is a published-package consumption pattern, not an in-repo one. The product stance is now: **every AlexaVoxCraft package that can legitimately participate in runtime application code should support Native AOT, including `Http`, `InSkillPurchasing`, and `Smapi`** (§9, §13). The `APLValueConverterFactory`/`APLValueCollectionConverterFactory` `MakeGenericType` hazard (§5, §8) is resolved not by scattering ~78 per-property `CustomConverter` registrations across ~90 model files (the prior recommendation), but by replacing the two factories' reflective `CreateConverterInternal`/`CreateConverter` bodies with a closed, compile-time-safe dispatch table built once inside the factory itself — centralizing converter-selection knowledge in the two files that already own it, rather than scattering it across every model class that happens to declare an `APLValue<T>`/`APLValueCollection<T>` property (§8, §12, §13 step 7 — revised recommendation, chosen over both a scattered-registration design and a source-generated one). Both remediation shapes are hand-written, not generated: no new source generator is needed, and extending the unrelated MediatR DI interceptor generator is not the right tool for it. Separately, one **pre-existing correctness bug** — `APLValue<Component>` resolving to `System.ComponentModel.Component` instead of the intended `APLComponent` (§8, §14) — must be fixed *before* the closed-type inventory backing either factory's dispatch table is finalized, since the AOT architecture should be built against the intended type, not an accidental one. This is the smallest architecture that satisfies the stated product requirement without breaking the existing polymorphic-converter design, which does not need to change.

## 2. Current architecture

### Packages and target frameworks

Confirmed via `src/Directory.Build.props:5`: all `src/` packages except `AlexaVoxCraft.MediatR.Generators` multi-target `net8.0;net9.0;net10.0;net11.0`. `AlexaVoxCraft.MediatR.Generators` targets `netstandard2.0` only (it is a Roslyn source generator — it runs inside the compiler process at consumer build time, never at consumer runtime, so its TFM is irrelevant to the AOT/runtime discussion; see `src/AlexaVoxCraft.MediatR.Generators/AlexaVoxCraft.MediatR.Generators.csproj`).

Packages (from `src/`):
- `AlexaVoxCraft.Model` — core request/response/directive/card models, JSON converters, `AlexaJsonOptions`/`AlexaTypeResolver`.
- `AlexaVoxCraft.Model.Apl` — APL component/command/document models and their own converters, layered on `AlexaJsonOptions`.
- `AlexaVoxCraft.Model.InSkillPurchasing` — ISP-specific models.

- `AlexaVoxCraft.MediatR.Generators` — the Roslyn incremental source generator (compile-time only, `netstandard2.0`).
- `AlexaVoxCraft.MediatR.Lambda` — AWS Lambda hosting (`AlexaSkillFunction`), `AlexaLambdaSerializer : ILambdaSerializer`.
- `AlexaVoxCraft.Lambda` — a second, apparently-parallel Lambda hosting/serialization surface with its own `AlexaLambdaSerializer` (`src/AlexaVoxCraft.Lambda/Serialization/AlexaLambdaSerializer.cs`).
- `AlexaVoxCraft.MinimalLambda` — a minimal-hosting-model alternative (`ActivatorUtilities.CreateInstance<THandler>` usage, `src/AlexaVoxCraft.MinimalLambda/Extensions/ServiceCollectionExtensions.cs:50`).
- `AlexaVoxCraft.Observability` — opt-in OpenTelemetry registration.
- `AlexaVoxCraft.Http` — a base HTTP client (`BaseClient`) used by SMAPI/ISP clients, with its own default `JsonSerializerOptions`.
- `AlexaVoxCraft.Smapi` — SMAPI developer API client, interaction-model builders. Not tooling-only: per product-owner clarification, SMAPI clients are also invoked from application code running inside Lambda functions in real, published-package consumers (§9) — invisible from this repo's own `ProjectReference` graph, which shows no in-repo consumer.
- `AlexaVoxCraft.InSkillPurchasing` — ISP domain logic.

### Consumer execution model

The documented entry point (CLAUDE.md, `docs/components/source-generation.md`, and `samples/Sample.Skill.Function/Function.cs`) is:

```csharp
// Program.cs
return await LambdaHostExtensions.RunAlexaSkill<Function, SkillRequest, SkillResponse>();

// Function.cs
public class Function : AlexaSkillFunction<SkillRequest, SkillResponse>
{
    protected override void Init(IHostBuilder builder)
    {
        builder
            .UseHandler<LambdaHandler, SkillRequest, SkillResponse>()
            .ConfigureServices((context, services) =>
            {
                services.AddSkillMediator(context.Configuration);
            });
    }
}
```

`AddSkillMediator` is, by default, intercepted at compile time by the C# 12 interceptor-based source generator in `AlexaVoxCraft.MediatR.Generators` (documented in `docs/components/source-generation.md`), which replaces handler/behavior/interceptor registration with direct, non-reflective `services.AddTransient<...>()` calls. This is real prior art for "treat trimming/AOT as an architectural constraint and solve it with source generation" — but it only solves DI *registration*. It does nothing for JSON, and does nothing for the mediator's runtime *dispatch* (`SkillMediator.Send`, §5), which still uses `Activator.CreateInstance`/`MakeGenericType`.

## 3. Current serialization pipeline

### The single shared `JsonSerializerOptions`

`AlexaJsonOptions` (`src/AlexaVoxCraft.Model/Serialization/AlexaJsonOptions.cs`) is a static class exposing `DefaultOptions`, built lazily and cached with a version-counter invalidation scheme:

```csharp
// AlexaJsonOptions.cs:50-77
private static JsonSerializerOptions CreateOptions()
{
    var resolver = new AlexaTypeResolver();
    resolver.Modifiers.Add(Modifiers.SetNumberHandlingModifier);
    foreach (var modifier in _modifiers) resolver.Modifiers.Add(modifier);

    var options = new JsonSerializerOptions
    {
        TypeInfoResolver = resolver,
        ReadCommentHandling = JsonCommentHandling.Skip
    };
    options.Converters.Add(new ObjectConverter());
    foreach (var converter in _converters) options.Converters.Add(converter);
    return options;
}
```

`AlexaTypeResolver : DefaultJsonTypeInfoResolver` (`src/AlexaVoxCraft.Model/Serialization/AlexaTypeResolver.cs:8`) overrides `GetTypeInfo` to call `base.GetTypeInfo` (the reflection-based path) and then post-process three specific types' `ShouldSerialize` delegates (`ResponseBody.Directives`, `Reprompt.Directives`, `ImageSource.Width/Height`). This is a conditional-serialization concern (functionally equivalent to `[JsonIgnore(Condition=...)]` with a runtime predicate), not a discriminator/polymorphism concern — it is fully expressible in a source-generated `JsonTypeInfo` via a `[JsonSourceGenerationOptions]`-driven modifier that STJ source-gen explicitly supports (`IJsonTypeInfoResolver` + `Action<JsonTypeInfo>` modifiers compose the same way regardless of whether the base resolver is reflection- or source-gen-based).

`AlexaJsonOptions` also exposes two *mutable, static, process-wide* extension points used pervasively by `AlexaVoxCraft.Model.Apl`:

```csharp
public static void RegisterConverter<T>(JsonConverter<T> converter) where T : notnull
public static void RegisterTypeModifier<T>(Action<JsonTypeInfo> modifier)
```

Nearly every APL model type (`Text`, `Container`, `Image`, `AlexaCard`, ~90 types total) has a static `RegisterTypeInfo<T>()` method that calls `AlexaJsonOptions.RegisterTypeModifier<T>(...)` to attach a `CustomConverter` to one specific property of its generated `JsonTypeInfo` (example: `src/AlexaVoxCraft.Model.Apl/Components/Text.cs:32-40` attaches an `APLCommandListConverter` to the `onTextLayout` property). These registrations are **not automatic** — they require the consumer to call `AplSupport.Add()` once at startup (`src/AlexaVoxCraft.Model.Apl/APLSupport.cs:14-134`, invoked from `samples/Sample.Apl.Function/Program.cs:6`). `AplSupport.Add()` also registers the built-in polymorphic-discriminator entries into `RequestConverter`/directive-handler extension points (`RenderDocumentDirective.AddSupport()`, `UserEventRequestHandler.AddToRequestConverter()`, etc.) — i.e., this bootstrap method is simultaneously the mechanism for (a) attaching custom per-property converters and (b) registering the closed set of APL-specific discriminated types into the shared converters. It is a real, if implicit, "type registration" extensibility point that a source-gen redesign needs to either preserve or replace with an explicit `[JsonSerializable]` list.

### Two independent `AlexaLambdaSerializer` implementations

- `src/AlexaVoxCraft.MediatR.Lambda/Serialization/AlexaLambdaSerializer.cs:17-21` and `src/AlexaVoxCraft.Lambda/Serialization/AlexaLambdaSerializer.cs:23-26` both implement `Amazon.Lambda.Core.ILambdaSerializer` directly (not AWS's own `SourceGeneratorLambdaJsonSerializer<T>` base class), take an optional consumer-supplied `JsonSerializerOptions?` in their constructor, and fall back to `AlexaJsonOptions.DefaultOptions` when null. Both call the generic `JsonSerializer.Deserialize<T>(stream, _options)` / `JsonSerializer.Serialize(stream, response, _options)` overloads. This is the actual request/response boundary for a Lambda-hosted skill: `requestStream -> AlexaLambdaSerializer.Deserialize<SkillRequest>() -> SkillMediator.Send() -> AlexaLambdaSerializer.Serialize(SkillResponse)`.
- `AlexaSkillFunction.cs:88` and `MinimalLambda`'s `ServiceCollectionExtensions.cs:41` both do `services.AddSingleton(AlexaJsonOptions.DefaultOptions)` — i.e. DI-register the same static singleton, so a consumer *can* today override it process-wide by registering their own `JsonSerializerOptions` before/instead of this call, but there is no first-class, documented API for "give me the built-in resolver plus my own types."

### Other independent `JsonSerializerOptions` construction sites (backward-compat risk surface, §10)

- `src/AlexaVoxCraft.Http/Clients/BaseClient.cs:36-41` — a **separate** default `new JsonSerializerOptions { PropertyNamingPolicy = CamelCase, ... }` with no `TypeInfoResolver` set (implicit reflection fallback), used by SMAPI/ISP HTTP clients (`AlexaSkillInvocationClient`, `src/AlexaVoxCraft.Smapi/Clients/AlexaSkillInvocationClient.cs:22`, constructs its own instance similarly).
- `src/AlexaVoxCraft.Smapi/Builders/InteractionModel/InteractionModelBuilder.cs:183` — another ad hoc default options instance.
- `src/AlexaVoxCraft.Model.Apl/DataStore/AccessTokenClient.cs:19` — `new(JsonSerializerDefaults.Web)`, also reflection-default.

None of these three are wired to `AlexaTypeResolver`/`AlexaJsonOptions` at all — they are independent reflection-based configurations. This means the AOT problem is not confined to `AlexaJsonOptions`; it exists in at least four independently-constructed `JsonSerializerOptions` across the solution, each of which would need either a `TypeInfoResolver` assignment or an explicit, documented "this surface is JIT-only" carve-out.

### `BaseClient` — generic `TResult`, arbitrary consumer types

```csharp
// BaseClient.cs:273, :295, :328
result = JsonSerializer.Deserialize<TResult>(rawResponse, JsonSerializerOptions);
content = new StringContent(JsonSerializer.Serialize(body, JsonSerializerOptions), ...);
```

`TResult`/`body` are generic type parameters supplied by whatever calls `BaseClient`'s protected methods — currently only `AlexaVoxCraft.Smapi`'s own model types, but the API shape is open (`protected async Task<TResult?> ...<TResult>(...)`). This is a second "arbitrary consumer/library type flows through reflection JSON" surface, structurally identical to `JsonAttributeBag` (§7).

### `JsonAttributeBag` — arbitrary consumer POCOs through the same reflection resolver

`src/AlexaVoxCraft.MediatR/Attributes/JsonAttributeBag.cs` (per the project's own MEMORY.md notes, this is the result of a prior "Attributes refactor" to `Dictionary<string, JsonElement>`) exposes:

```csharp
public void Set<T>(string key, T? value) => _values[key] = JsonSerializer.SerializeToElement(value, AlexaJsonOptions.DefaultOptions);
public T? Get<T>(string key) => ... element.Deserialize<T>(AlexaJsonOptions.DefaultOptions);
public bool TryGet<T>(string key, out T? value) => ...
public T GetRequired<T>(string key) => ...
```

`T` here is **the consumer's own session/persistent-attribute type** (a skill-specific game-state class, for example) — this is the single most important "consumer-owned type flowing through the library's serializer" surface in the whole codebase, and it is entirely dependent on `AlexaJsonOptions.DefaultOptions` staying reflection-capable unless the library gives consumers a way to register their own type metadata into that same options instance (§7).

### `IPersistenceAdapter`

Per MEMORY.md, `IPersistenceAdapter` methods operate on `IDictionary<string, JsonElement>` — i.e., the adapter boundary (typically a DynamoDB/S3-backed adapter) never needs to deserialize to a concrete consumer type itself; that deserialization happens later, on demand, via `JsonAttributeBag.Get<T>`. This is a good architectural fact for AOT: the storage layer is JSON-shape-agnostic (`JsonElement` in, `JsonElement` out), so the only place arbitrary-consumer-type deserialization actually happens is `JsonAttributeBag`.

### Test infrastructure as a wire-compatibility safety net

`test/AlexaVoxCraft.Model.Tests/Snapshots` contains 63 files and `test/AlexaVoxCraft.Model.Apl.Tests/Snapshots` contains 144 files (Verify-based snapshot tests, confirmed via `grep -rl "VerifyJson\|Verify("` matching `RequestVerificationTests.cs` and others), plus `test/AlexaVoxCraft.Model.Tests/Examples` and `test/AlexaVoxCraft.Model.Apl.Tests/Examples` directories of real/CloudWatch-derived JSON fixtures (per `docs/plans/0002-cloudwatch-driven-verify-tests-and-warning-cleanup.md`, these were deliberately captured from a **production** Lambda's CloudWatch logs, sanitized, and used to replace legacy hand-written fixtures — i.e. they already represent realistic wire shapes, not synthetic edge cases only). This is a strong existing asset for proving byte-identical output across a source-gen migration (§9, §11).

## 4. Previous AOT attempt and assessment

Git history across all branches (`git log --all --oneline -S"..."` for `JsonSerializerContext`, `RequiresDynamicCode`, `RequiresUnreferencedCode`, `PublishAot`, `IsTrimmable`, `JsonSourceGenerationOptions`) returns **no hits** for any of those terms anywhere in this repository's history. There is no branch, tag, or commit that ever introduced a `JsonSerializerContext`, `[JsonSerializable]`, or any `IsAotCompatible`/`PublishAot` configuration. The only historical trace even adjacent to Native AOT is:

- `DynamicallyAccessedMembersAttribute` usage, introduced in commit `6064978` ("Feature/apl support (#17)") and still present today at `src/AlexaVoxCraft.Model/Response/Converters/JsonStringEnumConverterWithEnumMemberAttrSupport.cs:43-44`:

  ```csharp
  public class JsonStringEnumConverterWithEnumMemberAttrSupport<
      [DynamicallyAccessedMembers(DynamicallyAccessedMemberTypes.PublicFields)] TEnum> : JsonConverter<TEnum>
      where TEnum : struct, Enum
  ```

  This converter's `Read`/`Write` delegate to `EnumHelper` (`src/AlexaVoxCraft.Model/Helpers/EnumHelper.cs`):

  ```csharp
  // EnumHelper.cs:18-22 (TryParseEnumWithEnumMemberSupport)
  var map = _enumLookup.GetOrAdd(enumType, type =>
      type.GetFields(BindingFlags.Public | BindingFlags.Static)
          .ToDictionary(
              f => f.GetCustomAttribute<EnumMemberAttribute>()?.Value ?? f.Name,
              f => (object)Enum.Parse(type, f.Name)));
  ```

  and similarly `ToEnumString<TEnum>` (`EnumHelper.cs:40-51`) does `enumType.GetField(name)?.GetCustomAttribute<EnumMemberAttribute>()`. Both call sites are cached per-`Type` in a `ConcurrentDictionary`, so the reflection cost is paid once per distinct enum type, not per call.

- The same file (lines 7-41) contains a large **commented-out** earlier design that instead subclassed STJ's own `JsonStringEnumConverter<TEnum>` and supplied a custom `JsonNamingPolicy` computed via the same `GetFields`/`EnumMemberAttribute` reflection, wrapped in a `private sealed class EnumMemberNamingPolicy`. This was abandoned in favor of the current hand-rolled `JsonConverter<TEnum>` implementation, evidently because `JsonStringEnumConverter<TEnum>`'s naming-policy hook did not give enough control (it computes names for *all* values up front via the policy, which doesn't cleanly support a fallback-value-on-unrecognized-input feature that the current converter has via `FallbackValue`).

**Assessment — is this correct, and should it be kept, redesigned, or removed?**

- The `[DynamicallyAccessedMembers(PublicFields)]` annotation is *directionally correct but incomplete*, and it was almost certainly added by someone reasoning "this generic type parameter reflects over fields, so I should annotate it" rather than as part of a deliberate, tested AOT initiative — there is no corresponding `IsTrimmable`/`PublishAot` test anywhere that would have validated it, and no commit message or doc references AOT/trimming as the reason. Technically: `DynamicallyAccessedMemberTypes.PublicFields` tells the trimmer to preserve the enum's public static fields when `TEnum` is used as a generic argument at a call site the trimmer can see; ILLink by default also preserves the custom attribute *data* on a preserved member (attribute-removal is a separate, opt-in trimming feature, not the default), so `GetCustomAttribute<EnumMemberAttribute>()` should keep working under ordinary trimming. However: (a) this converter's `TEnum` is only ever closed over compile-time-fixed concrete enum types within the AlexaVoxCraft assemblies themselves (e.g., wherever it's applied via `[JsonConverter(typeof(JsonStringEnumConverterWithEnumMemberAttrSupport<SomeEnum>))]`), so the annotation is *reachable and effective* for those call sites — this part is genuinely fine. (b) It does nothing about the vastly larger reflection surface in `AlexaTypeResolver : DefaultJsonTypeInfoResolver`, which is the actual, dominant AOT/trim hazard for the whole options pipeline; fixing the enum converter while leaving `DefaultJsonTypeInfoResolver` as the base resolver has **zero net effect** on whether a consumer can `PublishAot` successfully, because the options object as a whole is still fundamentally reflection-based. (c) The reflection here (`GetFields`/`GetCustomAttribute`) is not a `RequiresDynamicCode`-class hazard (no codegen, no `MakeGenericType`) — it is purely a trimming-preservation concern, and a well-annotated one at that.

- **Recommendation for this narrow piece**: keep the `[DynamicallyAccessedMembers]` annotation (it's correct and cheap), but it should not be presented or relied upon as evidence of AOT-readiness elsewhere in the codebase — it solves 1 of the many places reflection appears, and it does not solve the dominant one. If AlexaVoxCraft moves to a source-generated `JsonSerializerContext` design (§12-13), a source-generated context would use `JsonStringEnumConverter<TEnum>`-shaped generation for its own enums or continue to delegate to this custom converter (custom converters ARE compatible with source-gen contexts, confirmed in §6) — either way this file survives largely unchanged; only the *base resolver* it's registered into needs to change.
- The commented-out alternate design should simply be deleted as dead code when this file is next touched — it documents an abandoned approach, not a currently-relevant AOT plan, and leaving ~35 lines of commented-out reflection-based code in a converter file invites a future reader to mistake it for a deliberate roadmap.

No other historical branch or PR attempted anything resembling STJ source generation, `IJsonTypeInfoResolver` composition, or a documented AOT strategy. The `docs/components/lambda-hosting.md:538-548` "Bundle Size Optimization" section recommends enabling `PublishTrimmed`/`TrimMode=copyused` **but explicitly roots (exempts from trimming) `AlexaVoxCraft.Model` and `AlexaVoxCraft.Model.Apl`** via `<TrimmerRootAssembly>`:

```xml
<PropertyGroup>
  <PublishTrimmed>true</PublishTrimmed>
  <TrimMode>copyused</TrimMode>
</PropertyGroup>
<ItemGroup>
  <TrimmerRootAssembly Include="AlexaVoxCraft.Model" />
  <TrimmerRootAssembly Include="AlexaVoxCraft.Model.Apl" />
</ItemGroup>
```

This is the closest thing to an explicit, written acknowledgment in the repo that these two assemblies are **not trim-safe today** — the documented workaround is to exempt them from trimming entirely (keep 100% of their IL/metadata), which defeats the size-reduction goal of trimming for exactly the packages that matter most, and does not help with Native AOT at all (`TrimmerRootAssembly` has no meaning under `PublishAot`; AOT trims everything not statically reachable, with no equivalent escape hatch for reflection-based resolvers — `PublishAot` will either fail to compile the reflection-heavy path or throw `InvalidOperationException` at runtime once `JsonSerializerIsReflectionEnabledByDefault` is forced to `false`).

## 5. AOT/trimming hazard audit

Findings below combine direct reading of `src/` (this agent) with an independent parallel audit (background research agent) that searched the same tree for the same categories; both converge on the same conclusions. Classification buckets per the brief: (1) actual AOT blocker, (2) trimming concern, (3) analyzer-warning-only, (4) harmless reflection, (5) reflection statically preservable, (6) fundamentally conflicts with Native AOT.

## 6. System.Text.Json findings

Current Microsoft guidance (fetched from Microsoft Learn / dotnet/runtime docs, all URLs below), synthesized against the findings above:

- **Source generation fundamentals.** A `JsonSerializerContext`-derived partial class with `[JsonSerializable(typeof(T))]` per type generates compile-time `JsonTypeInfo<T>` metadata. Two modes exist: full **metadata mode** (supports polymorphism, converters, everything) and a perf-only **fast-path/serialization-optimization mode** that does *not* support polymorphism. AlexaVoxCraft's heavy reliance on discriminator-based polymorphism (§8) means it must use metadata mode, not fast-path-only generation. Source: [How to use source generation in System.Text.Json](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/source-generation).

- **`IJsonTypeInfoResolver` composition — the exact pattern for a library + consumer split.** `JsonTypeInfoResolver.Combine(...)` merges multiple `IJsonTypeInfoResolver` instances (each queried in order, first non-null `JsonTypeInfo` wins); `JsonSerializerOptions.TypeInfoResolverChain` is the mutable list form of the same idea. A `JsonSerializerContext.Default` property *is* an `IJsonTypeInfoResolver`. This is precisely the documented mechanism for "library ships a generated context, consumer combines it with their own": `new JsonSerializerOptions { TypeInfoResolver = JsonTypeInfoResolver.Combine(AlexaVoxCraftContext.Default, MySkillContext.Default) }`. Sources: [source-generation doc](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/source-generation), [`JsonTypeInfoResolver.Combine` API reference](https://learn.microsoft.com/en-us/dotnet/api/system.text.json.serialization.metadata.jsontypeinforesolver.combine).

- **`IsReflectionEnabledByDefault` and the trimmed/AOT runtime break — precise model.** There are four distinct things in play here, which the prior research pass conflated; re-verified against current Microsoft Learn content (fetched 2026-09-08):

  1. **No resolver supplied at all.** If a consumer constructs `new JsonSerializerOptions()` (or calls a `JsonSerializer.Serialize/Deserialize` overload with no options) and never sets `TypeInfoResolver`/`TypeInfoResolverChain`, STJ falls back to `DefaultJsonTypeInfoResolver` **only if** `JsonSerializer.IsReflectionEnabledByDefault` is `true`. That property "gets a value that indicates whether unconfigured `JsonSerializerOptions` instances should default to the reflection-based `DefaultJsonTypeInfoResolver`" and is backed by the `System.Text.Json.JsonSerializer.IsReflectionEnabledByDefault` `AppContext` switch (MSBuild property `JsonSerializerIsReflectionEnabledByDefault`), which defaults to `true`. Confirmed via the .NET breaking-change note: "projects that have the `PublishTrimmed` property enabled now automatically turn off the reflection-based defaults of System.Text.Json" — i.e. `PublishTrimmed=true` (and therefore `PublishAot=true`) sets `JsonSerializerIsReflectionEnabledByDefault` to `false` automatically, and `JsonSerializer.Serialize(new { Value = 42 })` (no resolver) then throws `InvalidOperationException: Reflection-based serialization has been disabled for this application.` **at runtime**, not at build time. This is case (1); it does not apply to AlexaVoxCraft as written, because `AlexaJsonOptions.CreateOptions()` always explicitly sets `TypeInfoResolver = resolver` (`AlexaJsonOptions.cs:63`) — the implicit-default fallback is never exercised.
  2. **Explicitly constructing `DefaultJsonTypeInfoResolver` (this repo's actual situation).** `AlexaTypeResolver : DefaultJsonTypeInfoResolver` (`AlexaTypeResolver.cs:8`) is unconditionally `new`'d up in `AlexaJsonOptions.CreateOptions()` regardless of `JsonSerializer.IsReflectionEnabledByDefault`. This is **not gated behind the feature switch at all** — it is ordinary, always-reachable reflection code, and under `PublishAot`/`PublishTrimmed` it either throws at the point `DefaultJsonTypeInfoResolver`'s internals attempt reflection over an unrecognized type, or (more likely, since the AOT/trim analyzers will see a live, unconditional `new DefaultJsonTypeInfoResolver()` call) it produces `IL2026`/`IL3050`-class analyzer warnings and the linker is *not* able to prove the reflection path unreachable, because there is no branch to eliminate — the constructor call is unconditional. This is the precise reason `AlexaJsonOptions`'s current design is a hard AOT blocker rather than a soft one: it is fundamentally different from case (3) below, which is written so the linker *can* remove the reflection path.
  3. **An intentional, gated JIT-only reflection fallback.** The documented, AOT-safe pattern for "reflection when available, generated metadata otherwise" is: `TypeInfoResolver = JsonSerializer.IsReflectionEnabledByDefault ? new DefaultJsonTypeInfoResolver() : MyContext.Default;`. Because `JsonSerializer.IsReflectionEnabledByDefault` is treated as a **link-time constant** by the trimmer/AOT compiler (it is backed by a feature-switch `AppContext` value that publish-time tooling can prove statically, exactly like `RuntimeFeature.IsDynamicCodeSupported`), and because `PublishAot=true` forces that switch to `false` at publish time, the linker can statically prove the `? new DefaultJsonTypeInfoResolver()` branch is never taken and **removes it entirely from the AOT-published binary** — it does not root `DefaultJsonTypeInfoResolver`'s reflection code, and no analyzer warning fires for that dead branch. This is the mechanism the brief asked to verify precisely, and it is confirmed: it is exactly why this ternary pattern is the standard recommended way to give JIT consumers effortless reflection support for arbitrary POCOs while keeping an app AOT-clean — a real, usable strategy AlexaVoxCraft could adopt (weighed as Alternative E in §12/§7 of this document) but does not today, because `AlexaTypeResolver`'s construction (case 2) is unconditional, not gated behind this switch.
  4. **The AOT-safe generated-resolver path.** A `JsonSerializerContext`-derived `.Default` (or a chain built from one via `JsonTypeInfoResolver.Combine`) requires no feature-switch gating at all — it is ordinary generated code, present and correct in every build configuration, JIT or AOT.

  **Correction to the prior pass**: `AlexaTypeResolver : DefaultJsonTypeInfoResolver` is case (2), not case (1) or (3) — it behaves differently from "STJ's implicit reflection default" because it is an explicit, always-constructed subclass, not an unconfigured-options fallback, and unlike case (3) it is never wrapped in an `IsReflectionEnabledByDefault` check, so the AOT compiler cannot eliminate it. Fixing this requires either replacing the unconditional `new AlexaTypeResolver()` with a generated context (§7-8, the recommended direction), or rewriting it into the case-(3) shape (`IsReflectionEnabledByDefault ? new AlexaTypeResolver() : GeneratedContext.Default`) if the JIT-reflection-fallback alternative (§12) is adopted instead. Sources: [`JsonSerializer.IsReflectionEnabledByDefault`](https://learn.microsoft.com/en-us/dotnet/api/system.text.json.jsonserializer.isreflectionenabledbydefault), [Breaking change: `PublishTrimmed` and reflection-based JSON serialization](https://learn.microsoft.com/en-us/dotnet/core/compatibility/serialization/8.0/publishtrimmed) (fetched 2026-09-08; confirms both the `AppContext` default and the link-time-constant/branch-elimination behavior).

- **`AlexaJsonOptions.RegisterTypeModifier<T>` composes with a generated-context resolver via `JsonTypeInfoResolver.WithAddedModifier` — proof, not assumption.** `DefaultJsonTypeInfoResolver.Modifiers` (the `IList<Action<JsonTypeInfo>>` `AlexaTypeResolver` currently populates, `AlexaJsonOptions.cs:53-59`) is a member specific to `DefaultJsonTypeInfoResolver` and has no equivalent on a generated `JsonSerializerContext`. However, `System.Text.Json.Serialization.Metadata.JsonTypeInfoResolver.WithAddedModifier(this IJsonTypeInfoResolver resolver, Action<JsonTypeInfo> modifier)` (introduced .NET 8, confirmed via Microsoft Learn API reference and the .NET 8 STJ blog post) works over **any** `IJsonTypeInfoResolver`, including a `JsonSerializerContext.Default` or the result of `JsonTypeInfoResolver.Combine(...)`, and "extends the `DefaultJsonTypeInfoResolver.Modifiers` API to any `IJsonTypeInfoResolver` instance." A modifier added via `.WithAddedModifier(...)` runs against whatever `JsonTypeInfo` the *wrapped* resolver produced, immediately after that resolver produces it — so to reproduce today's "one global modifier list, manually filtered by `ti.Type == typeof(T)` inside the delegate" semantics (`AlexaJsonOptions.cs:92-101`) across a chain that may contain more than one context, the modifier must be applied to the *outermost* combined resolver (i.e. `JsonTypeInfoResolver.Combine(ModelContext.Default, AplContext.Default, ...).WithAddedModifier(wrappedModifier)`), not to an individual inner context — applied there, it fires regardless of which resolver in the chain actually produced the `JsonTypeInfo`, exactly matching today's behavior. §7's proposed `AlexaJsonOptions.RegisterTypeInfoResolver(IJsonTypeInfoResolver)` extension point is therefore compatible with this: `CreateOptions()` would build `IJsonTypeInfoResolver resolver = JsonTypeInfoResolver.Combine(ModelContext.Default, ...consumer-registered resolvers...);` then apply `Modifiers.SetNumberHandlingModifier` first and each `_modifiers` entry in registration order via repeated `.WithAddedModifier(...)` calls, preserving both the existing built-in `ShouldSerialize` conditional-property logic (§3) and every APL `RegisterTypeInfo<T>()` call site unchanged. **Cache/versioning**: `AlexaJsonOptions`'s existing version-counter cache invalidation (`_version`/`_cachedVersion`, `AlexaJsonOptions.cs:14-46`) already rebuilds `DefaultOptions` lazily on next access after *any* `RegisterConverter`/`RegisterTypeModifier` call — there is no "freeze on first use" today, so registering a modifier after `DefaultOptions` has already been read once is already fully supported and requires no change; this is a design fact worth stating with confidence rather than re-verifying, since the code makes it unambiguous (a version bump plus `_cachedOptions = null` under lock, checked lazily on next `get`). This directly closes the "does not still support registering modifiers before first use" / "registering after first use" question: both already work today, and nothing about switching the base resolver from `DefaultJsonTypeInfoResolver` to a generated context changes that — only the *construction* of `resolver` inside `CreateOptions()` changes. Sources: [`JsonTypeInfoResolver.WithAddedModifier`](https://learn.microsoft.com/en-us/dotnet/api/system.text.json.serialization.metadata.jsontypeinforesolver.withaddedmodifier), [What's new in System.Text.Json in .NET 8](https://devblogs.microsoft.com/dotnet/system-text-json-in-dotnet-8/).

- **Polymorphism in source-gen.** `[JsonPolymorphic]`/`[JsonDerivedType]` (STJ's own attribute-based polymorphism, .NET 7+) *are* supported by metadata-mode source generation, for statically-known, closed hierarchies. AlexaVoxCraft does **not** currently use these attributes anywhere (confirmed by grep) — its polymorphism is entirely hand-rolled via custom `JsonConverter<T>` subclasses with runtime discriminator dictionaries (§3, §8). Both approaches are AOT-legitimate: **a hand-written `JsonConverter<T>` is fully AOT/trim-safe as long as its own `Read`/`Write` avoid reflection**, and STJ's source generator explicitly supports delegating to custom converters registered via `[JsonConverter(typeof(X))]` or `options.Converters`. This means AlexaVoxCraft does **not** need to rewrite its converters as `[JsonPolymorphic]`/`[JsonDerivedType]` hierarchies to become AOT-compatible — it needs its `JsonSerializerOptions.TypeInfoResolver` to stop being `DefaultJsonTypeInfoResolver`, while keeping the existing custom converters registered on top of a generated context. `JsonConverterFactory` (used by `APLValueConverterFactory`, `APLValueCollectionConverterFactory`) is the pattern Microsoft flags as AOT-risky when it does `MakeGenericType`/`Activator.CreateInstance` internally with an unbounded generic parameter — §8 exhaustively enumerates both factories' generic parameter sets (48 + 30 closed instantiations, confirmed closed and package-owned) and §13 step 7 recommends the specific replacement. Sources: [Polymorphic serialization](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/polymorphism); known friction case worth re-checking against current runtime: [dotnet/runtime #85884, cross-assembly polymorphic source-gen](https://github.com/dotnet/runtime/issues/85884).

- **General library-author AOT/trim guidance.** `IsTrimmable=true` marks an assembly trim-compatible and turns on trim warnings; `IsAotCompatible=true` implies `IsTrimmable=true` plus AOT/single-file analyzers. Neither is set anywhere in this repo today (§5). Two-tier validation is explicitly recommended by Microsoft: (a) `EnableTrimAnalyzer`/`EnableAotAnalyzer` on the library itself catches issues visible from the library's own code, but (b) full validation requires a **separate test app** that references the library, roots it (`TrimmerRootAssembly`), and is actually `dotnet publish`ed with `PublishTrimmed`/`PublishAot=true` — because "the analysis results depend on the implementation details of the dependencies," which the library-only analyzer run cannot see. This directly substantiates the brief's insistence that "does it build" is not "does it work." Source: [Prepare .NET libraries for trimming](https://learn.microsoft.com/en-us/dotnet/core/deploying/trimming/prepare-libraries-for-trimming).

- **AWS Lambda + Native AOT.** AWS's supported pattern for .NET Lambda + Native AOT pairs `LambdaBootstrapBuilder.Create()` with `Amazon.Lambda.Serialization.SystemTextJson`'s `SourceGeneratorLambdaJsonSerializer<T>`, which *requires* a consumer/function-supplied `JsonSerializerContext` covering the Lambda's input/output types (described in AWS's own samples as mandatory under AOT), targeting the `provided.al2023` custom runtime that this repo already documents (`docs/components/lambda-hosting.md`). AlexaVoxCraft's own `AlexaLambdaSerializer` implementations (`AlexaVoxCraft.MediatR.Lambda` and `AlexaVoxCraft.Lambda`) do **not** derive from or delegate to `SourceGeneratorLambdaJsonSerializer<T>` — they implement `ILambdaSerializer` directly and always use `AlexaJsonOptions.DefaultOptions` or a consumer-supplied `JsonSerializerOptions`. This is actually convenient: because AlexaVoxCraft owns its own `ILambdaSerializer` implementation rather than delegating to AWS's generic-context-based one, fixing `AlexaJsonOptions`'s resolver fixes the Lambda boundary too, without needing a second, AWS-specific `JsonSerializerContext` at the host layer — but it does mean AlexaVoxCraft is fully responsible for its own AOT correctness at this boundary; it cannot lean on AWS's serializer doing the right thing. (Primary AWS doc page fetch failed with HTTP 405 during this research; findings above are corroborated by AWS sample-repository patterns but the canonical `docs.aws.amazon.com/lambda/latest/dg/dotnet-native-aot.html` page should be independently re-fetched before this claim is used in an ADR.)

## 7. Package-owned vs consumer-owned serialization metadata

This is the central design fork, per the brief. Evidence-grounded options:

**Types fully owned by AlexaVoxCraft at compile time** (candidates for a library-owned `JsonSerializerContext`): `SkillRequest`/`SkillResponse` and all `Request`/`Directive`/`Card`/`OutputSpeech` subtypes in `AlexaVoxCraft.Model`; all APL component/command/document/data-source types in `AlexaVoxCraft.Model.Apl`; ISP models in `AlexaVoxCraft.Model.InSkillPurchasing`; SMAPI models in `AlexaVoxCraft.Smapi`. All of these are closed sets — every concrete type reachable from `RequestConverter`, `BasePolymorphicConverter<T>` subclasses, and `APLComponentConverter`'s dictionary is enumerable today by reading `AplSupport.Add()` and the individual `*Converter`/`*Resolver` classes (§3, §8). This set can and should be covered by one or more `[JsonSerializable]`-annotated `JsonSerializerContext` classes shipped by the library.

**Types introduced by a consumer** — three distinct surfaces, evidenced above:
1. `JsonAttributeBag.Get<T>/Set<T>/TryGet<T>/GetRequired<T>` (`src/AlexaVoxCraft.MediatR/Attributes/JsonAttributeBag.cs:44,54,68,87`) — genuinely arbitrary, skill-specific POCOs, always routed through `AlexaJsonOptions.DefaultOptions`.
2. `BaseClient.Deserialize<TResult>`/`Serialize<T>` (`BaseClient.cs:273,295,328`) — currently only exercised with AlexaVoxCraft-owned SMAPI/ISP types (confirmed: `InSkillPurchasingClient : BaseClient` at `src/AlexaVoxCraft.InSkillPurchasing/Clients/InSkillPurchasingClient.cs:10` and the SMAPI clients are the only subclasses in the solution), but the API shape is generically open.
3. A custom `IDirective`/`IRequestTypeResolver` registered via `DirectiveConverter.RegisterDirectiveDerivedType<TDirective>(key)` or `RequestConverter.RegisterRequestTypeResolver<TResolver>()` (§8) — both ultimately still call the non-generic `JsonSerializer.Deserialize(json, resultType, options)` overload with a consumer-supplied `resultType`, so they have the same requirement as (1)/(2): `options`'s resolver chain must be able to produce `JsonTypeInfo` for that consumer type.

**The proposed contract for all three is identical and is sufficient, verified against how each dispatches**: a consumer supplies their own `[JsonSerializable]`-annotated `JsonSerializerContext` (covering their attribute POCOs, their `TResult`/`body` types, and/or their custom `IDirective`/request type) and appends it once via the new `AlexaJsonOptions.RegisterTypeInfoResolver(IJsonTypeInfoResolver)` method (or a `RegisterContext<TContext>()` convenience overload). Because `DirectiveConverter.Read`/`RequestConverter.Read` and `JsonAttributeBag`/`BaseClient` all route through the same shared `JsonSerializerOptions.TypeInfoResolver` chain, one registration call covers every one of these surfaces simultaneously — there is no separate metadata-wiring step needed per API. This is not an assumption: `BasePolymorphicConverter<T>.Write` and `.Read` (§8) call `JsonSerializer.Serialize/Deserialize(..., value.GetType()/resultType, options)`, the exact non-generic overload a combined resolver chain services correctly for any type declared in any resolver in the chain, library- or consumer-owned alike.

**Asymmetry between the two directive/request extension points, evidenced (§8, resolved from "unsupported assumed" to "confirmed either way")**: `RegisterDirectiveDerivedType<TDirective>` carries real XML doc comments describing consumer-facing intent (`DirectiveConverter.cs:31-35`, "Registers a derived `IDirective` type for deserialization...") and has 8 real call sites spanning three packages (§8) — it is an actively used, real extension seam and must keep working under the contract above. `RequestConverter.RegisterRequestTypeResolver<TResolver>()` has no XML doc comment, no mention anywhere in `docs/`, and (per full-repo grep) no confirmed caller outside `AlexaVoxCraft.Model` itself — but per the brief's instruction not to assume "no observed external usage" means "unsupported," it receives the exact same AOT contract as `RegisterDirectiveDerivedType<T>`, because the underlying dispatch mechanism (`RequestConverter.Read`, non-generic `Deserialize(json, resultType, options)`) is structurally identical. The only real difference between the two APIs is the strength of the evidence that anyone uses the public one — not the technical treatment.

For both, the only reflection-free architecture is: `AlexaJsonOptions.DefaultOptions`'s `TypeInfoResolver` becomes a **chain** (`JsonTypeInfoResolver.Combine(AlexaVoxCraftContext.Default, ...)`) that a consumer can append to, either by (a) exposing a public, documented API such as `AlexaJsonOptions.RegisterTypeInfoResolver(IJsonTypeInfoResolver)` / `AlexaJsonOptions.RegisterContext<TContext>()` that consumers call once at startup (mirroring the existing `RegisterConverter<T>`/`RegisterTypeModifier<T>` pattern already in the codebase — same shape, same call-site ergonomics, no new mental model for existing users), or (b) a first-class DI-registered `JsonSerializerOptions` (already partially possible today via `services.AddSingleton(...)`, just needs to be the documented, supported path rather than an incidental side effect of `AlexaSkillFunction.cs:88`). Option (a) is the smaller change and matches the brief's "prefer the smallest architecture" and "should feel natural for normal non-AOT consumers too" principles, since it reuses an idiom (`AlexaJsonOptions.RegisterX<T>(...)`, called once at startup, mutates a process-wide cached options object) that APL consumers already use today via `AplSupport.Add()`.

**Models considered, per the brief's instruction not to assume an answer:**

| Model | AOT correctness | Consumer ergonomics | Compatibility | Maintenance |
|---|---|---|---|---|
| AlexaVoxCraft owns everything, no consumer participation | Fails for `JsonAttributeBag`/`BaseClient` open-`T` surfaces — cannot be made correct without either removing those APIs or accepting they remain JIT-only | Best-case ergonomics if it worked, but it doesn't for the actual public API surface | N/A — doesn't solve the real problem | N/A |
| AlexaVoxCraft owns closed framework types + exposes a resolver-chain extension point consumers append their own generated context to | Fully correct: closed types get a generated context; open types get consumer-owned generated contexts, combined via `JsonTypeInfoResolver.Combine` | One new call at startup (`AlexaJsonOptions.RegisterTypeInfoResolver(MyContext.Default)`), same shape as existing `RegisterConverter`/`RegisterTypeModifier` | Fully backward compatible: JIT consumers who never call the new method keep working exactly as today (reflection resolver can remain the fallback tail of the chain for them, §10) | Library maintains its own context (mechanical, generator-driven); no burden from consumer types |
| Consumer-supplied `JsonSerializerOptions` entirely replaces the library's (no chain) | Correct only if consumer manually re-registers every AlexaVoxCraft type + all `RegisterTypeModifier` side effects — fragile, error-prone, easy to silently break directive serialization shape | Poor — consumer must reimplement plumbing the library already has | Backward-incompatible in spirit (defeats the point of a shared library default) | High: consumers debug library-shape bugs themselves |
| Generic APIs accepting `JsonTypeInfo<T>` per call (no shared options object at all) | Correct but heavyweight | Poor — every `Get<T>`/`Deserialize<T>` call site needs an explicit `JsonTypeInfo<T>` argument, a significant API-shape change | Breaking | Pushes complexity to every call site instead of one startup registration |
| Separate source-generator NuGet package that consumers reference to *generate* their own context, wired automatically | Correct, but adds a second package dependency and second source generator for consumers to reason about | Extra ceremony beyond "add a package reference"; probably unnecessary given STJ's own `JsonSerializerContext` generator already does this job for free once a consumer declares one `[JsonSerializable]` partial class | Non-breaking addition, but redundant with STJ's built-in generator | Extra maintenance burden with no clear benefit over just documenting "add your own `JsonSerializerContext`, combine it" | 

**Conclusion for this section**: the second row (library owns closed types + resolver-chain extension point) is the only option that is both AOT-correct and non-breaking, and it reuses an idiom this codebase already has (`AlexaJsonOptions.RegisterX<T>`). This is elaborated as the recommended direction in §13.

**Context granularity and visibility — settled by the actual package/assembly dependency graph, not a preference.** Reading every `src/*/*.csproj`'s `<ProjectReference>` items (same graph used for the Http/Smapi analysis in §9) settles this precisely rather than leaving it "needs a prototype":
- `AlexaVoxCraft.Model` has **zero** project references — it is the dependency root. It cannot know about `AlexaVoxCraft.Model.Apl` or `AlexaVoxCraft.Model.InSkillPurchasing` types, full stop; the dependency direction forbids a single, all-encompassing context living in `Model`.
- `AlexaVoxCraft.Model.Apl` references `Model` (one-directional). `AlexaVoxCraft.Model.InSkillPurchasing` references `Model` only (not `Model.Apl`).
- This means **one context per package that owns closed model types is not a stylistic choice, it's the only shape the dependency graph allows**: a `Model`-owned context for `Request`/`Directive`/`Card`/etc. base types, a separate `Model.Apl`-owned context for APL component/command/document types, a separate `Model.InSkillPurchasing`-owned context for ISP models. A single monolithic context is architecturally impossible without inverting a dependency (making `Model` reference `Model.Apl`, which would be a much larger, unrelated redesign) or duplicating type declarations across contexts (worse than the status quo).
- **How each package registers its own context without an upward dependency**: `AlexaVoxCraft.Model`'s context is the unconditional base of `AlexaJsonOptions.CreateOptions()`'s resolver chain (it already lives in the same assembly as `AlexaJsonOptions`, so no new wiring mechanism is needed there). `AplSupport.Add()` (`src/AlexaVoxCraft.Model.Apl/APLSupport.cs:14-134`) already is the established, consumer-called bootstrap hook that lives in `Model.Apl` and can freely call into `Model`'s public static API (the dependency direction permits `Model.Apl → Model`) — so `AplSupport.Add()` gains one more line, `AlexaJsonOptions.RegisterTypeInfoResolver(AplModelContext.Default)`, alongside its existing `RegisterTypeInfo<T>()`/discriminator-registration calls, with zero new architecture. **`Model.InSkillPurchasing` does not need a new bootstrap method invented for this — one already exists** (correcting the prior pass, which assumed none did): `InSkillPurchasingSupport.Add()` (`src/AlexaVoxCraft.Model.InSkillPurchasing/InSkillPurchasingSupport.cs:9-19`) is the package's existing, documented ("Call this once at application startup before processing skill requests") consumer-facing entry point — it already registers `PaymentDirective.AddSupport()` and `ConnectionResponseHandler.AddSupport()` into the shared `DirectiveConverter`/`RequestConverter` discriminator tables, exactly mirroring what `AplSupport.Add()` does for APL. It gains the identical one extra line, `AlexaJsonOptions.RegisterTypeInfoResolver(InSkillPurchasingModelContext.Default)`, with zero new public surface (§7 revised; §13 step 4).
- **Should the generated context classes be public?** No — challenged directly, and the answer is no. The only thing that needs to cross a package boundary is an already-realized `IJsonTypeInfoResolver` instance (a context's `.Default` property, which is `IJsonTypeInfoResolver`-typed) flowing into `AlexaJsonOptions.RegisterTypeInfoResolver(IJsonTypeInfoResolver)`. Nothing about that call requires the `JsonSerializerContext`-derived *class* itself to be `public` — it can be `internal` to its own assembly, referenced only by that assembly's own bootstrap code (`CreateOptions()` for `Model`'s context, `AplSupport.Add()` for `Model.Apl`'s). This keeps AlexaVoxCraft's generated-code surface entirely out of its public API (smaller public surface, freedom to restructure/split/merge contexts later without a breaking change, less generated-code noise in IntelliSense/docs for consumers who never need to see it) while still giving genuinely external consumers (who need to register *their own* context for `JsonAttributeBag`/`BaseClient`/custom-directive types, §7 above) the one public hook they actually need: `RegisterTypeInfoResolver`, which only requires an `IJsonTypeInfoResolver` — their own context can be public to them without AlexaVoxCraft's needing to be public to anyone.
- **`AlexaVoxCraft.Http`, `AlexaVoxCraft.InSkillPurchasing`, and `AlexaVoxCraft.Smapi` also do not need a new bootstrap API invented — each has an existing consumer-facing startup/config path this rides along on for free, evidenced directly:**
  - **`AlexaVoxCraft.InSkillPurchasing`** (the HTTP/runtime package, distinct from `Model.InSkillPurchasing` above): consumers already call `services.AddInSkillPurchasing()` (`src/AlexaVoxCraft.InSkillPurchasing/ServiceCollectionExtensions.cs:20`) once at startup to register `IInSkillPurchasingClient`/`InSkillPurchasingClient` via `AddHttpClient<...>(...)`. `InSkillPurchasingClient` (`Clients/InSkillPurchasingClient.cs:17-20`) always calls `BaseClient`'s 2-arg constructor, which today builds its own ad hoc, unwired `new JsonSerializerOptions{...}` (`src/AlexaVoxCraft.Http/Clients/BaseClient.cs:36-44`). No new public method is needed: either (a) `BaseClient`'s existing 2-arg constructor is changed to build its default options from a `Http`-owned resolver chain instead of a bare `new JsonSerializerOptions{...}`, or (b) `AddInSkillPurchasing()` itself supplies a `JsonSerializerOptions` (built from the ISP-owned context) to the `AddHttpClient` registration. Either way, the existing, already-mandatory `AddInSkillPurchasing()` call is the ride-along point — no new ceremony for consumers.
  - **`AlexaVoxCraft.Http`** itself ships no service-collection-level bootstrap of its own (only `HttpClientBuilderExtensions.AddAuthorizationForwarding()`, `src/AlexaVoxCraft.Http/HttpClientBuilderExtensions.cs:17-22`, which is about auth, not JSON) — its real "consumption path" is `BaseClient`'s own constructor, since every subclass (`InSkillPurchasingClient`, `AlexaSkillInvocationClient`, `AlexaInteractionModelClient`) either takes `BaseClient`'s 2-arg constructor (implicit default options) or passes its own ad hoc options explicitly to the 3-arg constructor. The zero-new-ceremony fix is inside `BaseClient` itself: change what the 2-arg constructor's default `JsonSerializerOptions` is built from (§9), not add a new public registration method.
  - **`AlexaVoxCraft.Smapi`** already has real, documented DI extension methods consumers call today: `AddSmapiDeveloperClient(...)` and `AddSkillInvocationClient(...)` (`src/AlexaVoxCraft.Smapi/ServiceCollectionExtensions.cs:42,85,136,183`), each registering an `AddHttpClient<...>` client backed by `BaseClient`. `AlexaSkillInvocationClient`'s constructor (`Clients/AlexaSkillInvocationClient.cs:20-28`) explicitly passes its own ad hoc `new JsonSerializerOptions{...}` to `BaseClient`'s 3-arg constructor; `AlexaInteractionModelClient` (`Clients/AlexaInteractionModelClient.cs:17-18`) uses the 2-arg (implicit default) constructor; `InteractionModelBuilder.ToJson(JsonSerializerOptions? options = null)` (`Builders/InteractionModel/InteractionModelBuilder.cs:177-190`) falls back to yet another ad hoc reflection-default instance when the consumer passes none. None of these four call sites needs a new public bootstrap method — the existing `AddSmapiDeveloperClient`/`AddSkillInvocationClient` extensions are already the mandatory startup call for any consumer using these clients, and `InteractionModelBuilder.ToJson`'s existing optional-`options` parameter already gives a consumer an override point without any new surface. The fix is to change what each client's *default* options is built from (a `Smapi`-owned context for `InteractionModelDefinition`/model-authoring types, chained the same way as `Model`/`Model.Apl`), not to add registration ceremony.
  - **Contrast with APL, where a bootstrap call genuinely is new-ish public surface but is *already required and free to extend***: `AplSupport.Add()` is not a new invention for this migration — it already exists and consumers already must call it for APL support, so adding one resolver-registration line to it costs nothing new. The lesson generalizes, not to "give every package an `X.Add()` bootstrap," but to "find whatever existing required call already exists for that package and extend it" — which, for `Http`/`InSkillPurchasing`/`Smapi`, is a constructor default or an existing DI extension method, not a new `.Add()`-style static class.
- **Finer-than-per-package splitting (e.g. separate Request vs. Response contexts within `Model`)**: no evidence in this pass justifies it — STJ source-gen's generated-code size scales with declared `[JsonSerializable]` count regardless of how many context classes those declarations are spread across (splitting doesn't reduce total generated code, it only changes how it's partitioned across files/build units), and per-package is already the natural, dependency-graph-enforced unit; the recommendation is exactly one context per package that owns closed model types (`Model`, `Model.Apl`, `Model.InSkillPurchasing`), no finer, unless a future prototype's build-time/generated-IL measurements say otherwise.

## 8. Polymorphism findings

Every polymorphic/discriminator-driven hierarchy examined resolves via a **closed, compile-time-enumerable dictionary of `typeof(X)` literals**, never via `Type.GetType(string)`, assembly scanning, or open-ended runtime discovery:

- **`Request` hierarchy** (`RequestConverter.cs:9-17`): a static `List<IRequestTypeResolver>` (`DefaultRequestTypeResolver`, `AudioPlayerRequestTypeResolver`, `PlaybackRequestTypeResolver`, `TemplateEventRequestTypeResolver`, `SkillEventRequestTypeResolver`, `SkillConnectionRequestTypeResolver`, `ConnectionResponseTypeResolver`), each presumably mapping a `type` discriminator string to a compile-time-known `Type` (confirmed for the base pattern; individual resolver internals should be spot-checked before an ADR, but the overall `Read` method (`RequestConverter.cs:37-70`) reads the discriminator via `JsonDocument`, asks each resolver `CanResolve(requestType)`, then calls `typeResolver.Resolve(requestType)` → a `Type`, then `JsonSerializer.Deserialize(json, target, options)` — the non-generic, runtime-`Type` overload. A public `RegisterRequestTypeResolver<TResolver>()` extension point exists (`RequestConverter.cs:20-28`) but today is only ever invoked internally by `AplSupport.Add()` for the built-in APL request types — there is no evidence any third-party consumer extends this hierarchy, and it is not documented as a public extension point anywhere in `docs/`.
- **`Directive`, `Card`, `ResponseBody`, `OutputSpeech`, `ConnectionTask`** — same `BasePolymorphicConverter<T>` base (`BasePolymorphicConverter.cs`), same shape: `protected abstract IDictionary<string, Type> DerivedTypes` (a closed dictionary literal in each subclass) plus an optional `DataDrivenTypeFactories` (`IDictionary<string, Func<JsonElement, Type>>`) for cases where the discriminator alone isn't sufficient and a small amount of the payload must be inspected to pick the type (still resolves to a compile-time-known `Type`, just via a function instead of a flat lookup — still closed, still AOT-safe). Unlike `RequestConverter`, `DirectiveConverter` (`src/AlexaVoxCraft.Model/Response/Converters/DirectiveConverter.cs:7,37`) exposes a confirmed, **actively used** public extension point: `public static void RegisterDirectiveDerivedType<TDirective>(string key) where TDirective : IDirective`. This is called from at least 8 real call sites across two packages — `SendIndexListDataDirective.cs:12`, `UpdateIndexListDataDirective.cs:14`, `SendTokenListDataDirective.cs:12`, `RenderDocumentDirective.cs:23-25` (three separate discriminator keys mapped to the *same* `RenderDocumentDirective` type, for APL/APLT/APLA document-type variants), `ExecuteCommandsDirective.cs:17` (all in `AlexaVoxCraft.Model.Apl`), and `PaymentDirective.cs:40` (in `AlexaVoxCraft.Model.InSkillPurchasing`). This confirms the directive hierarchy's "closed set" is closed only *per package*, not per assembly: `AlexaVoxCraft.Model` ships the converter and its built-in discriminators, while `AlexaVoxCraft.Model.Apl` and `AlexaVoxCraft.Model.InSkillPurchasing` extend it at their own module-initialization time via this exact public API. Any source-gen redesign must preserve `RegisterDirectiveDerivedType<T>` as a real, load-bearing, multi-package extension seam — not just a theoretical one, unlike `RequestConverter.RegisterRequestTypeResolver<T>()` (§8 above), which today has no confirmed callers outside `AlexaVoxCraft.Model` itself.
- **APL component hierarchy** (`APLComponentConverter.cs:13-60+`): a `ConcurrentDictionary<string, Type>` literally built as `[nameof(Container)] = typeof(Container), [nameof(Image)] = typeof(Image), ...` for ~50+ component types — this is about as AOT-friendly a discriminator table as is possible to write by hand.
- **`APLValue<T>`/`APLValueCollection<T>` factories** (`APLValueConverterFactory.cs`, `APLValueCollectionConverterFactory.cs`) are `JsonConverterFactory` subclasses — the one shape STJ's own guidance flags as AOT-risky if their generic parameter set isn't closed. This research pass exhaustively enumerated every closed instantiation (full-repo grep of `src/`, `test/`, `samples/` for `APLValue<...>`/`APLValueCollection<...>` property declarations and nested usages, cross-checked against the two `JsonConverterFactory` implementations line-by-line):

  - **`APLValue<T>`**: 49 distinct closed instantiations found as public property types across `AlexaVoxCraft.Model.Apl` (`AVGPath.cs`, `APLComponent.cs`, and ~40 other component/command/document files). Of these, `APLValue<object>` (`Commands/SetValue.cs:19`) is already special-cased inside `APLValueConverterFactory.CreateConverterInternal` (`_aplObjectType`/`APLObjectConverter`, no `MakeGenericType` involved), leaving **48** that reach the `MakeGenericType(typeof(APLValueConverter<>), valueType)` branch. Of those 48: the large majority (~40) are `AlexaVoxCraft.Model.Apl`'s own enums (many as `Nullable<TEnum>`, e.g. `AlexaImageAlignment?`, `BlendMode?`, `KeyboardType?` — nullable and non-nullable count as separate closed generics for source-gen purposes), a handful are BCL primitives already reachable via any generated context (`bool`, `bool?`, `double`, `double?`, `int`, `int?`, `string`), one is `System.Uri` (`VideoSource`-adjacent properties), and one, `APLValue<Component>` (`Components/AlexaSwipeToAction.cs:179`, `Components/AlexaTextListItem.cs:28`), is very likely an unintentional defect: no type literally named `Component` exists anywhere in `AlexaVoxCraft.Model.Apl` or its namespace chain, so the unqualified `Component` resolves via the file's `using System.ComponentModel;` import to **`System.ComponentModel.Component`** (the WinForms-era BCL base class) rather than the presumably-intended `APLComponent` — a real, closed, but almost certainly wrong generic instantiation, flagged here as evidence, not fixed (out of scope per this research's constraints). **Sequencing (not merely a flagged defect): this bug must be fixed before, and separately from, the AOT migration** — whichever of the three converter-remediation designs compared in §12/§13 step 7 is implemented, its closed-type inventory is a *snapshot* of every `APLValue<T>`/`APLValueCollection<T>` instantiation the library ships, and that inventory must be taken against the *intended* type (`APLComponent`) rather than the accidental one (`System.ComponentModel.Component`), or the AOT architecture permanently encodes the bug as if it were a real requirement (a closed dispatch entry for a BCL WinForms type nothing in the object graph actually needs) and fixing it later becomes a breaking change to the generated/hand-written type inventory instead of a one-line pre-migration correction. Concretely: fix `AlexaSwipeToAction.cs:179`/`AlexaTextListItem.cs:28` (and their `using System.ComponentModel;` imports, if no longer needed) first, in its own PR, verified by the existing Verify snapshots (§3, §11) for those two components; only then enumerate/lock the closed-type inventory for §13 step 7. None of the 48 are consumer/external types; the codebase exposes no public API (no `RegisterComponent<T>`-equivalent — confirmed below) that lets a consumer add a new `APLValue<T>` property to the library's own serialized object graph.
  - **`APLValue<IEnumerable<T>>` shapes** (the `APLEnumerableValueConverter<TValue,TList>` `MakeGenericType` branch, `APLValueConverterFactory.cs:226-234`): confirmed via grep to be **unreachable in the current codebase** — zero properties anywhere declare `APLValue<IList<...>>`/`APLValue<List<...>>`/`APLValue<IEnumerable<...>>` directly. Every real enumerable-shaped `APLValue<T>` usage instead sets an explicit `CustomConverter = new GenericSingleOrListConverter<X>(...)` per property (5 call sites: `Layout.cs:63`, `Style.cs:41`, `APLTDocument.cs:30`, `ExecuteCommandsDirective.cs:51`, `Audio/AudioLayout.cs:53`), which STJ honors ahead of the type-level `[JsonConverter(factory)]` attribute and therefore never invokes this branch at all. This is dead code today, and simultaneously the existing in-repo template for how to eliminate the live branches.
  - **`APLValueCollection<T>`**: 30 distinct closed instantiations found (e.g. `APLComponent`, `APLCommand`, `APLAction`, `AlexaListItem`, `Parameter`, `int`, `string`, plus one genuinely nested case, `APLValueCollection<APLValue<int?>>` at `VectorGraphics/AVGPath.cs:40`, confirming composed closed generics also occur and must both be declared if source-gen metadata is used for this layer). All are AlexaVoxCraft.Model.Apl-owned or BCL-primitive; none are consumer types.
  - **Is the generic surface public/consumer-controlled?** `APLValue<T>`/`APLValueCollection<T>` are public generic classes with `[JsonConverter(typeof(...Factory))]` stamped on the *open* generic definition (`APLValue_T.cs:9`, `APLValueCollection_T.cs:17`), so the factory activates for **any** closed instantiation STJ ever resolves, under any `JsonSerializerOptions`, not just `AlexaJsonOptions.DefaultOptions` — a consumer *can* construct `new APLValue<TheirType>()` and, e.g., store it via `JsonAttributeBag.Set("k", myAplValue)`, which would reach this same factory. This is not a new hazard distinct from `JsonAttributeBag`'s already-identified open-`T` problem (§5, §7) — it's the same hazard, reachable through one more path — and the fix is the same: a consumer doing this must supply their own generated context covering `APLValue<TheirType>` via the resolver-chain extension point (§7). For the library's own closed object graph (`SkillRequest`/`SkillResponse`/APL documents), the set is genuinely closed, finite, and fully enumerated above — no `RegisterComponent<T>`-style public extension API exists (confirmed: `AplComponentConverter`'s `AplComponentLookup` dictionary is `private static`, `APLComponentConverter.cs:13`, with no registration method, unlike `DirectiveConverter`), so third-party consumers cannot add new closed-generic `APLValue<T>` instantiations into the library's own component/command/document types even if they wanted to.

**Converter-factory remediation — three designs compared, for long-term maintainability, not just AOT-safety (revises the prior pass's recommendation).** The prior pass recommended eliminating `APLValueConverterFactory`/`APLValueCollectionConverterFactory`'s `MakeGenericType` hazard by attaching an explicit `CustomConverter` to each of the ~78 individual properties (across ~90 model files, confirmed via `grep -rl "RegisterTypeInfo" src/AlexaVoxCraft.Model.Apl` → 104 files carry a `RegisterTypeInfo<T>()` method) that today rely on the ambient factory attribute, mirroring `Text.cs:32-40`'s existing `onTextLayout` → `APLCommandListConverter` pattern. Re-examined here against two alternatives, grounded in a full read of both factory files (`src/AlexaVoxCraft.Model.Apl/JsonConverter/APLValueConverterFactory.cs`, `APLValueCollectionConverterFactory.cs`):

- **(a) Per-property explicit `CustomConverter` registration (prior recommendation).** Mechanism: extend every `RegisterTypeInfo<T>()` method whose type owns an `APLValue<T>`/`APLValueCollection<T>`-typed property to look up that specific `JsonPropertyInfo` by name (`info.Properties.FirstOrDefault(p => p.Name == "...")`) and assign `.CustomConverter = new APLValueConverter<X>()` (or the collection/enumerable equivalent), exactly as `Text.cs:32-40` already does for `onTextLayout`. **AOT/analyzer behavior**: fully AOT-safe — no reflection anywhere in the assignment path. **Allocations/startup**: one `JsonPropertyInfo` lookup + one converter instantiation per property per `JsonTypeInfo` build, cached thereafter by STJ itself — comparable to (b)/(c). **Code size**: largest of the three — ~78 separate `RegisterTypeModifier<T>` call sites (one closure per property, most needing a `FirstOrDefault(p => p.Name == "...")` string lookup), spread across ~90 files that otherwise have nothing to do with JSON-metadata plumbing. **Maintainability — the deciding factor**: knowledge of "which CLR type does property X's `APLValue<T>` need" is scattered one property at a time, by property *name string*, across every component/command/document file in `AlexaVoxCraft.Model.Apl`; a future contributor adding a new `APLValue<SomeEnum>` property to an existing type must remember to also add a `RegisterTypeModifier<T>` entry naming that exact property, in a location unrelated to where the property itself is declared, with no compiler enforcement if they forget — the property would silently fall through to the (removed or `[RequiresDynamicCode]`-gated) factory reflection path instead of failing loudly. **Nullable/enum/nested generics**: each needs its own by-name property lookup + converter construction; `APLValueCollection<APLValue<int?>>` (`VectorGraphics/AVGPath.cs:40`) needs a nested `CustomConverter` composition per property, not merely per type. **Verdict**: technically sufficient, but the worst of the three on the stated criterion (smallest long-term maintenance boundary), because it maximizes scatter rather than minimizing it.

- **(b) Centralized closed dispatch inside the existing factories (recommended — see below).** Mechanism: keep `APLValueConverterFactory`/`APLValueCollectionConverterFactory` exactly as they are structurally today — still `JsonConverterFactory` subclasses, still attached via `[JsonConverter(typeof(...Factory))]` on the *open* generic type definitions `APLValue<T>`/`APLValueCollection<T>` (`APLValue_T.cs:9`, `APLValueCollection_T.cs:17`), still automatically invoked by STJ for every closed instantiation it encounters at any property, on any type, without any per-property registration anywhere — but replace `CreateConverterInternal`'s/`CreateConverter`'s bodies (`APLValueConverterFactory.cs:210-244`, `APLValueCollectionConverterFactory.cs:18-28`) with a closed, compile-time-safe dispatch instead of `Activator.CreateInstance(typeof(APLValueConverter<>).MakeGenericType(valueType), ...)`: either a chain of `if (valueType == typeof(X)) return new APLValueConverter<X>();` arms, or a `Dictionary<Type, Func<JsonConverter>>` built once in a static field and populated the same way `_dimensionTypes`/`_aplObjectType` are already built today (`APLValueConverterFactory.cs:186-189` — this pattern already exists in the file for the `APLValue<object>` special case; extending it to all 48/30 types is the same shape, not a new one). **AOT/analyzer behavior**: fully AOT-safe — every `new APLValueConverter<X>()` for a closed `X` is an ordinary, compile-time-visible generic instantiation the AOT compiler compiles ahead of time; nothing about `JsonConverterFactory`, `CanConvert`, or attribute-driven converter resolution is itself reflection-based or AOT-risky (§6 already establishes that custom converters, including factories whose *internals* avoid `MakeGenericType`, are fully source-gen/AOT-compatible). **Allocations/startup**: identical to (a) and today's factory — one dispatch + one converter construction per distinct closed generic type, cached in the existing `_converterCache`/no cache needed if converters are stateless singletons reused across calls (a further optimization available here, not available to (a)). **Code size**: smallest of the three by structure, though the dispatch table itself is not short — ~78 dispatch arms total, but concentrated in exactly 2 files (the two factories) instead of scattered across ~90; this is a code-*organization* win, not necessarily a raw line-count win, and it is the organization, not the count, that the "smallest long-term maintenance boundary" criterion is actually about. **Maintainability**: converter-selection knowledge lives in exactly the two places that already own "which converter handles which closed generic" as a concept — the factories themselves — so a future contributor adding a new `APLValue<SomeEnum>` property anywhere in the codebase needs no awareness of JSON-metadata plumbing at the property's declaration site at all; the *only* action required is one new dispatch-table entry in the relevant factory, discoverable by grepping the factory file, and if forgotten, produces an immediate, clear, first-use exception from the factory's own fallback arm (below) rather than a silent property-by-property gap. **Nullable/enum/nested generics**: nullable and non-nullable are simply two separate `typeof(X)`/`typeof(X?)` dispatch keys; `APLValueCollection<APLValue<int?>>` is one entry in `APLValueCollectionConverterFactory`'s own table (`itemType == typeof(APLValue<int?>)`), with no special-casing needed because `APLValue<int?>` itself continues to resolve recursively through `APLValueConverterFactory` exactly as it does today. **`APLValue<object>`'s existing special case**: already implemented as exactly this shape today (`_aplObjectType`/`APLObjectConverter`, `CreateConverterInternal`'s first `switch`, `APLValueConverterFactory.cs:212-221`) — (b) is a direct, minimal extension of a pattern already present in the file, not a new one. **The confirmed-unreachable `APLEnumerableValueConverter<TValue,TList>` branch**: removed from the closed dispatch table (it is provably unreached by any shipped type, §5/§8), but not deleted from the assembly — kept as a narrow, explicitly gated fallback arm, annotated `[RequiresDynamicCode]`/`[RequiresUnreferencedCode]`, reached only if `JsonSerializer.IsReflectionEnabledByDefault` is true (mirroring the settled JIT-fallback decision, item 5 below) and the incoming type isn't one of the closed 48/30 — i.e. a JIT-only escape hatch for a consumer who declares `APLValue<TheirEnumerableType>` outside the library's own object graph (the same open-`T` hazard already identified for `JsonAttributeBag`, §7/§8), never reachable in an AOT build. **Verdict**: satisfies the stated criterion best — smallest long-term maintenance *boundary* (exactly 2 files own this knowledge, forever, regardless of how many APL component/command types the library grows to), not merely fewest lines today.

- **(c) Generated centralized dispatch (a source generator emits the same table (b) would have).** Mechanism: a new Roslyn incremental generator scans `AlexaVoxCraft.Model.Apl`'s compilation for every `APLValue<T>`/`APLValueCollection<T>`-typed property/field and emits the closed dispatch table from (b) automatically, keeping it in sync as new properties are added. **AOT/analyzer behavior**: identical to (b) once generated — the emitted code has the same shape. **Allocations/startup**: identical to (b). **Generated code size**: same as (b)'s table, just machine-written instead of hand-written. **Maintainability — where this loses**: it requires standing up and maintaining a *second* Roslyn source generator in a repo that currently has exactly one (`AlexaVoxCraft.MediatR.Generators`), for a type universe that is small (78 entries), closed, and changes only when a human deliberately adds a new APL component/command to `Model.Apl` — an event that already requires touching that type's own file and, under (b), touching the relevant factory's dispatch table in the same PR; the generator does not remove meaningful toil (the "toil" is one line in a well-known file, not a repetitive multi-file chore) but does add a permanent maintenance surface of its own: a generator project to keep building against future Roslyn/SDK versions, its own test suite, and a second thing contributors must understand when a converter isn't found. Unlike (a), a forgotten entry under (c) genuinely cannot happen (the generator finds every property mechanically) — this is a real advantage over both (a) and (b) — but per the brief's explicit instruction not to default to generation just because a generator exists elsewhere in the repo, this advantage does not outweigh the ongoing cost of a second generator for a table this small and this rarely-changing, especially since (b)'s "forgotten entry" failure mode is already a loud, first-use exception (not silent), not a runtime-AOT-crash. **Verdict**: technically the most automated, but not justified by the evidence — the type universe doesn't grow fast enough or unpredictably enough to earn a second source generator, and (b) already gets the same centralization with materially less permanent machinery.

**Recommendation: (b) — centralized closed dispatch inside the existing factories.** This replaces the prior pass's ~78-per-property-registration recommendation (§1, §13 step 7, revised). It keeps `APLValueConverterFactory`/`APLValueCollectionConverterFactory`'s existing `JsonConverterFactory` shape and existing `[JsonConverter(factory)]` attribute placement — meaning zero changes to any of the ~90 `RegisterTypeInfo<T>()` methods across `AlexaVoxCraft.Model.Apl`, zero new source generator, and the smallest number of files that ever need to change when the closed-type universe grows.

**Can consumers extend these hierarchies today?** Mixed, and now resolved precisely rather than left as a blanket "closed": `DirectiveConverter.RegisterDirectiveDerivedType<T>()` is a real, documented-by-XML-comment, actively-used (8 call sites, 3 packages) extension point and must be preserved as such. `RequestConverter.RegisterRequestTypeResolver<T>()` is public but undocumented (no XML doc comment, no mention in `docs/`) and has no confirmed external caller — `AplSupport.Add()` (the only real-world caller found) only ever registers AlexaVoxCraft's own built-in types through it. `APLComponentConverter`'s component-type dictionary and the `APLValue<T>`/`APLValueCollection<T>` closed-generic surface behind it have **no public registration API at all** (§8 above) and are genuinely closed, full stop — not merely closed-by-convention. Per §7, all three surfaces get the identical AOT contract (consumer supplies a generated `JsonSerializerContext`, appends it via `AlexaJsonOptions.RegisterTypeInfoResolver`), so this mixed picture does not change the recommended remediation — it only changes which APIs a follow-on ADR should describe as "supported, documented extension points" (`RegisterDirectiveDerivedType<T>`) versus "public but unadvertised, kept working as a courtesy" (`RegisterRequestTypeResolver<T>`) versus "not extensible, closed set" (APL components/`APLValue<T>`).

**Would a `[JsonPolymorphic]`/`[JsonDerivedType]`-based redesign change wire compatibility?** Potentially, and unnecessarily. `[JsonDerivedType]` requires either a single discriminator property with STJ-controlled placement/ordering semantics or nested-type wrapping, both of which risk subtly changing output byte-shape versus the current hand-rolled `Read`/`Write` pair (which, per `BasePolymorphicConverter.Write`, simply calls `JsonSerializer.Serialize(writer, value, value.GetType(), options)` — i.e., write behavior is driven entirely by the runtime type's own `JsonTypeInfo`, with no injected discriminator-writing logic visible in this converter itself; each concrete type presumably serializes its own `type` property as a regular `[JsonPropertyName("type")]`-decorated member, e.g. `Text.Type` in `Components/Text.cs:21` — `public override string Type => nameof(Text);`). **Recommendation: do not migrate to `[JsonPolymorphic]`/`[JsonDerivedType]`.** Keep the existing custom converters (they are already AOT-legitimate per §6) and only change what base resolver services the underlying types they deserialize into. This is the lowest-risk path to wire-format byte-identity, directly testable via the existing 207 Verify snapshots (§3, §11). **`[JsonPolymorphic]`/`[JsonDerivedType]` are explicitly OUT OF SCOPE for this migration** (settled, not merely deferred): there is no demonstrated user need for STJ's built-in polymorphism attributes specifically — the existing hand-rolled converters already preserve the current wire model exactly, and switching carries only downside (wire-shape risk) with no offsetting AOT or product benefit, since §6 already establishes that hand-written converters are equally AOT-legitimate. Considered, rejected — no evidence-based need.

## 9. Target framework considerations

Confirmed TFMs (`src/Directory.Build.props:5`): `net8.0;net9.0;net10.0;net11.0` for every package except the source generator (`netstandard2.0`, compile-time only — no runtime AOT relevance). All four are >= net6.0, i.e. all are within STJ's/the runtime's Native AOT support window; there is no legacy-TFM carve-out needed (contrast with the general library guidance's `netstandard2.0`/`net472` gating advice, which does not apply here since this repo doesn't multi-target anything pre-net6.0 in its runtime-facing packages).

Given that, there is **no technical need for conditional compilation** to implement source-gen JSON support across these TFMs — `JsonSerializerContext`/`[JsonSerializable]` behave consistently across net8–net11, and a single shared implementation file works for all of them. The recommendation is therefore a single, TFM-independent `JsonSerializerContext` design, not per-TFM branches.

Should `IsAotCompatible` be set, and on which TFMs? **Not yet, and not on any TFM until the validation strategy in §11 has actually been executed.** Setting `IsAotCompatible=true` is a claim to consumers and to `dotnet publish` tooling; per Microsoft's own guidance (§6), that claim requires clean analyzer output *and* a real trimmed/AOT-published test app that runs correctly — neither exists today. Once the `AlexaJsonOptions` resolver is replaced and the mediator dispatch path (§5) is verified under a real AOT publish (both required — the mediator fix is a hard gate on this claim, §1/§13 step 8), `IsAotCompatible=true` could reasonably be set uniformly across `net8.0`–`net11.0` for every package that can legitimately participate in runtime application code (§9's corrected scope): `AlexaVoxCraft.Model`, `AlexaVoxCraft.Model.Apl`, `AlexaVoxCraft.Model.InSkillPurchasing`, `AlexaVoxCraft.MediatR`, `AlexaVoxCraft.MediatR.Lambda`, `AlexaVoxCraft.Http`, `AlexaVoxCraft.InSkillPurchasing`, and `AlexaVoxCraft.Smapi` — not merely the packages directly in the Lambda request/response path, since `Http`/`InSkillPurchasing`/`Smapi` are now confirmed runtime-participating (§9).

**`AlexaVoxCraft.Http`/`AlexaVoxCraft.Smapi` scope — corrected from the prior pass by explicit product-owner clarification, then re-audited against the code.** The prior pass inferred `Smapi` was tooling-only purely from this repo's internal `<ProjectReference>` graph: no in-repo package references `AlexaVoxCraft.Smapi`, so nothing in the runtime request path pulls it in transitively. **That inference was wrong.** Per product-owner clarification, SMAPI clients (`AlexaSkillInvocationClient`, `AlexaInteractionModelClient`) are also used from Lambda functions in real, published AlexaVoxCraft-based applications — a usage pattern invisible from this repo's own dependency graph because it is how *downstream, NuGet-consuming* skills use the published package, not how this repo's own samples wire it up. `AlexaVoxCraft.InSkillPurchasing`'s Lambda/mid-request usage (`InSkillPurchasingClient.GetProductsAsync`/`GetPurchasingEnabledAsync`/`GetTransactionsAsync`, `Clients/InSkillPurchasingClient.cs:23-44`, called from a handler mid-invocation to decide whether to offer a purchase) remains unquestionably in-scope for the same reason it was in the prior pass. **The corrected product stance, applied uniformly**: AlexaVoxCraft packages that can legitimately participate in runtime application code should support Native AOT, including `Http`, `InSkillPurchasing`, and `Smapi` — dependency-graph invisibility from *this* repo is not evidence of tooling-only status for a published library; it is evidence only that this repo's own samples don't happen to exercise the path.

**Audit of `Smapi`'s remaining JSON serialization paths under this corrected assumption** (grep of `src/AlexaVoxCraft.Smapi` confirms exactly three JSON-touching call sites, all independent of `AlexaJsonOptions`): (1) `AlexaSkillInvocationClient`'s constructor (`Clients/AlexaSkillInvocationClient.cs:20-28`) passes its own ad hoc `new JsonSerializerOptions { PropertyNamingPolicy = null, DefaultIgnoreCondition = WhenWritingNull, Encoder = UnsafeRelaxedJsonEscaping }` to `BaseClient`'s 3-arg constructor — reflection-default, unwired, and used by `InvokeAsync<TRequest, TResponse>` (`Clients/AlexaSkillInvocationClient.cs:31-46`), whose `TRequest`/`TResponse` are **genuinely open, consumer-supplied types** (arbitrary skill request/response bodies being invoked for testing) — structurally identical to `JsonAttributeBag`'s open-`T` hazard (§7), not a closed set. (2) `AlexaInteractionModelClient` (`Clients/AlexaInteractionModelClient.cs:17-18`) uses `BaseClient`'s 2-arg constructor, i.e. `BaseClient`'s own default reflection options (`BaseClient.cs:36-44`) — its `GetAsync`/`UpdateAsync` operate on `InteractionModelDefinition` (`Models/InteractionModel`), a closed, `Smapi`-owned model family. (3) `InteractionModelBuilder.ToJson(JsonSerializerOptions? options = null)` (`Builders/InteractionModel/InteractionModelBuilder.cs:177-190`) falls back to yet another ad hoc reflection-default instance when the consumer passes none, serializing the builder's own closed `InteractionModelDefinition` graph. **Conclusion**: `Smapi` needs its own package-owned resolver context, structurally like `Model`/`Model.Apl`/`Model.InSkillPurchasing`, covering the closed interaction-model/skill-management type family (`InteractionModelDefinition` and its component types) — *and* its `AlexaSkillInvocationClient.InvokeAsync<TRequest,TResponse>` open-`T` surface needs the same consumer-resolver-chain contract as `JsonAttributeBag`/`BaseClient.Deserialize<TResult>` (§7), since there is no way to close that generic parameter from inside the library. Today none of `Smapi`'s three call sites use any resolver at all — this is a green-field wiring job, not a rework of existing wiring.

**Recommendation (revised)**: bring both `Http` and `Smapi` into the same `[JsonSerializable]`-context/resolver-chain fix as `AlexaJsonOptions`, alongside `InSkillPurchasing` (already recommended in the prior pass for the reason above). `Http`'s `BaseClient.Deserialize<TResult>`/`Serialize<T>` generic-`T` surface (`BaseClient.cs:273,295,328`) is structurally identical to `JsonAttributeBag`'s and gets the same treatment — wire `BaseClient`'s default options to a resolver-chain-backed default (§7's zero-new-ceremony path: change what the constructor builds, not add a new method) instead of its own ad hoc `new JsonSerializerOptions{...}`. `Smapi` additionally needs its own closed context for `InteractionModelDefinition` and friends, registered the same way. All three — `Http`, `InSkillPurchasing`, `Smapi` — are now part of the "AlexaVoxCraft runtime packages are AOT-compatible" claim; none is deferred as tooling-only. `AlexaVoxCraft.Observability` and `AlexaVoxCraft.MinimalLambda` were not deeply audited in this pass and should be separately verified before inclusion.

## 10. Backward-compatibility considerations

**Terminology used precisely from here on (per this refinement pass)**: this document distinguishes **wire-semantic compatibility** — the actual product requirement: a payload produced before the migration deserializes to an equivalent object graph after it, and a payload produced after the migration is accepted by Alexa's runtime/a pre-migration consumer, i.e. *meaning* is preserved — from **byte/property-order identity** — literal byte-for-byte equality of serialized output, including JSON property emission order. AlexaVoxCraft does **not** publicly promise stable JSON property ordering anywhere: full-repo grep of `docs/` and CLAUDE.md found no statement asserting property order as contractual, and no test asserts ordering as a product guarantee — the 207 Verify snapshot files (§3, §11) check byte/property-order identity only because that's what a naive string-diff `Verify(...)` call happens to compare, which makes those snapshots an excellent **regression-detection tool** for catching unintended shape drift during a source-gen migration, not evidence of, or a reason to preserve, a public ordering contract. A source-gen migration is free to change property emission order (STJ source-gen's default member ordering can differ subtly from `DefaultJsonTypeInfoResolver`'s reflection-based ordering) as long as wire-semantic compatibility holds; any resulting Verify snapshot diffs are expected, mechanical re-recordings, not compatibility regressions, and should be judged by re-deserializing the new output and confirming an equivalent object graph, not by string equality with the old snapshot. Every other section of this document that says "byte-identical" is describing the *validation technique* (§11) or the *low-risk expectation* for the closed, built-in model types specifically (§10 below) — not a claim that AlexaVoxCraft promises stable property ordering to consumers.

- **Existing serialization config APIs**: `AlexaJsonOptions.RegisterConverter<T>`/`RegisterTypeModifier<T>` are public, static, and used by ~90 call sites internally plus (implicitly) by any consumer who has learned this idiom from the APL package's pattern. Any redesign must preserve these method signatures and semantics — they should keep working exactly as today, just against a differently-constructed base resolver.
- **Consumers who supply their own `JsonSerializerOptions`** (`AlexaLambdaSerializer`'s constructor parameter, `BaseClient`'s constructor overload): these consumers already own their own reflection-or-not choice and are unaffected by changes to `AlexaJsonOptions.DefaultOptions` — but if they pass a plain reflection-based `JsonSerializerOptions` today and expect it to "just work" under a future AOT-supported release, that expectation needs explicit documentation as still being JIT-only (a consumer opting into AlexaVoxCraft's own AOT-safe default should not need to supply their own options at all, unless they have custom consumer types — see §7).
- **Changing the default resolver changes behavior only if reflection currently produces output that is not wire-semantically equivalent to what a generated context would produce** — for the closed, built-in model types, output should be at least wire-semantically equivalent, and in practice very likely byte/property-order identical too (verifiable via §11, and reusable as a regression guard even though it is not itself the product requirement — see the terminology note above); the risk is concentrated in subtle STJ default-resolver behaviors (property ordering, extension-data handling, naming-policy edge cases, enum default handling) that a hand-written generated context might reproduce slightly differently unless the migration is done carefully and validated snapshot-by-snapshot.
- **Naming policy, null handling, case sensitivity, unknown properties, extension data**: none of `AlexaJsonOptions.CreateOptions()`'s current settings (`ReadCommentHandling = Skip` is the only explicit option set beyond the resolver and converters) rely on anything STJ source-gen doesn't support identically — this is a low-risk area.
- **A precedent for a large, non-breaking, reflection-elimination migration already exists in this codebase**: the MediatR DI source generator (`docs/components/source-generation.md`, "Migration from Runtime Registration" section) explicitly documents that `AddSkillMediator()` changed from always-reflection to intercepted-by-default with **zero required consumer code changes** ("No code changes needed - existing handlers work with source generation automatically"), while still supporting an explicit opt-out (`EnableMediatRGeneratorInterceptor=false`) for anyone who needs the old behavior. This is a strong, concrete template for how the JSON migration should be positioned: default to the new, AOT-safe resolver; keep a documented, explicit escape hatch back to a fully-reflection-based `JsonSerializerOptions` for JIT-only consumers who hit an edge case, rather than removing reflection support outright.
- **Smallest viable public API addition**: one new method on `AlexaJsonOptions`, e.g. `RegisterTypeInfoResolver(IJsonTypeInfoResolver resolver)` (or `RegisterContext<TContext>() where TContext : JsonSerializerContext, new()`), appended to the internal resolver chain ahead of (or instead of) the reflection fallback. No changes to any existing public method signature are required by this design.

## 11. Validation strategy

Per the brief, "does it build" and "clean analyzer output" are necessary but explicitly insufficient. Proposed strategy, grounded in what already exists in this repo:

1. **A real, separate console/Lambda test application** (not a unit test project) that references the actual NuGet-equivalent project references (or, in CI, the actual packed packages) for `AlexaVoxCraft.Model`, `AlexaVoxCraft.Model.Apl`, `AlexaVoxCraft.MediatR`, `AlexaVoxCraft.MediatR.Lambda`, uses the normal public API exactly as `samples/Sample.Skill.Function` and `samples/Sample.Apl.Function` already do, and is built with `<PublishAot>true</PublishAot>`, `<InvariantGlobalization>true</InvariantGlobalization>` (Lambda-typical), `<EnableTrimAnalyzer>true</EnableTrimAnalyzer>`, `<EnableAotAnalyzer>true</EnableAotAnalyzer>`, `<JsonSerializerIsReflectionEnabledByDefault>false</JsonSerializerIsReflectionEnabledByDefault>` (force the exact failure mode a real AOT-published consumer would hit, rather than letting it silently stay true).
2. **Feed it the existing, realistic fixtures**: the 207 files already under `test/AlexaVoxCraft.Model.Tests/Snapshots` + `.../Examples` and `test/AlexaVoxCraft.Model.Apl.Tests/Snapshots` + `.../Examples` are CloudWatch-derived, production-realistic Alexa request/response payloads (per `docs/plans/0002-cloudwatch-driven-verify-tests-and-warning-cleanup.md`). The AOT test app should deserialize a representative subset (at minimum: a `LaunchRequest`, an `IntentRequest` with slots, a `SessionEndedRequest`, an APL `UserEventRequest`, and one of each currently-supported directive/card/APL-component family), run them through actual handler dispatch (`SkillMediator.Send`, exercising the `MakeGenericType`/`Activator.CreateInstance` path from §5 for real), and serialize representative responses (including at least one with APL directives, since that's the largest and most reflection-dependent surface via `AplSupport.Add()`'s ~90 `RegisterTypeInfo<T>()` registrations).
3. **Publish the AOT binary and actually execute it** (`dotnet publish -r <rid> -p:PublishAot=true`, then run the resulting native executable directly, not `dotnet run`), asserting on stdout/exit code/serialized output — not merely that `dotnet publish` exits 0. This directly operationalizes the brief's "the resulting native binary actually executed and its output validated" requirement.
4. **Byte-identity check against existing snapshots**: reuse the existing Verify snapshot files as the oracle — the AOT test app's serialized output for the same fixture inputs should be diffed against the corresponding `.verified.*` files already checked into `test/AlexaVoxCraft.Model.Tests/Snapshots` / `.../Model.Apl.Tests/Snapshots`. Any byte-level difference between JIT-reflection output and AOT-source-gen output is either a real wire-format regression (must be fixed) or reveals a snapshot that was itself accidentally reflection-dependent-shape (needs investigation either way). This reuses the single most valuable existing test asset without requiring it to be redesigned, per the brief's explicit "don't redesign these tests" instruction.
5. **CI wiring**: a dedicated CI job (separate from the existing `dotnet test`-based Testing Platform runs) that runs steps 1-4 on at least one Linux RID matching the Lambda `provided.al2023` runtime target (`linux-x64` and/or `linux-arm64`, matching `docs/components/lambda-hosting.md`'s documented Lambda configuration), gated on every PR that touches `src/AlexaVoxCraft.Model*`, `src/AlexaVoxCraft.MediatR*`, or the eventual `JsonSerializerContext` implementation files. A failure here should block merge exactly like a unit test failure — this is the mechanism that keeps "AOT-compatible" true over time rather than true only at the moment it was first claimed.
6. **Explicit analyzer settings to adopt on the shipping packages themselves** (not just the test app), once §12-13's redesign lands, re-verified against current Microsoft Learn content (fetched 2026-09-08, [Prepare .NET libraries for trimming](https://learn.microsoft.com/en-us/dotnet/core/deploying/trimming/prepare-libraries-for-trimming)): setting `<IsAotCompatible>true</IsAotCompatible>` on a project **transitively defaults** `IsTrimmable=true`, `EnableTrimAnalyzer=true`, `EnableSingleFileAnalyzer=true`, and `EnableAotAnalyzer=true` — confirmed by the doc's explicit statement, "The `IsTrimmable` property defaults to `true` when configuring a project as AOT-compatible with `<IsAotCompatible>true</IsAotCompatible>`," and by the related MSBuild-property description that `IsAotCompatible=true` implies the other three analyzer switches. This means the prior pass's two-step "`IsTrimmable` first, then `IsAotCompatible` later" sequencing is still reasonable as a *soak* strategy (see fewer warnings first, fix them, then take the bigger claim) but is not technically required by tooling — setting `IsAotCompatible=true` directly would turn on everything at once. Recommendation unchanged in substance: soak with `IsTrimmable`/`EnableTrimAnalyzer` first, set `IsAotCompatible=true` only after steps 3-4 above pass consistently in CI (§9).
7. **`VerifyReferenceAotCompatibility` — investigated, not recommended as a mandatory gate yet.** This MSBuild property (paired with `IsAotCompatible=true`) makes the AOT analyzer additionally check that every *referenced* assembly is itself annotated `[assembly: AssemblyMetadata("IsAotCompatible", "True")]`, surfacing `IL3058` for any that aren't (mirroring `VerifyReferenceTrimCompatibility`/`IL2125` for trimming). Checking this repo's actual dependency graph (`src/*/*.csproj`) against what's discoverable about each dependency's AOT status: (a) **`AlexaVoxCraft.MediatR` does not depend on the third-party `MediatR` NuGet package at all** — no `PackageReference Include="MediatR"` exists anywhere in the solution (confirmed by grep); `SkillMediator` is a from-scratch, same-named implementation, so the well-known fact that the *jbogard/MediatR* package is reflection-based and not yet fully AOT-annotated is irrelevant here — there is no such external dependency to be noisy. (b) The real dependencies most likely to be AOT-noisy are `Amazon.Lambda.RuntimeSupport`/`Amazon.Lambda.Serialization.SystemTextJson`/`Amazon.Lambda.Core` (`AlexaVoxCraft.MediatR.Lambda.csproj`) and `Serilog.AspNetCore`/`Serilog.Enrichers.Activity`/`LayeredCraft.Logging.CompactJsonFormatter` (same project) — AWS's own Lambda .NET tooling has been actively updated to support Native AOT (AWS's `.NET 10 runtime now available in AWS Lambda` post and the `dotnet-native-aot` Lambda deployment guide both describe `Amazon.Lambda.RuntimeSupport` + `LambdaBootstrapBuilder` as the supported AOT hosting path), but whether these specific package *versions* currently carry `IsAotCompatible=true` metadata was not independently confirmed in this pass (would require inspecting the installed package's assembly metadata, not just release notes) — this is exactly the kind of "noisy or not" question `VerifyReferenceAotCompatibility` would answer empirically, cheaply, once turned on. Serilog's ecosystem has historically leaned on reflection-based sinks/enrichers and its AOT-annotation status across the specific packages here is unverified. **Recommendation**: enable `VerifyReferenceAotCompatibility` on the `AlexaVoxCraft.Model*`/`AlexaVoxCraft.MediatR*` projects as soon as `IsAotCompatible=true` is set on them (step 6), but do **not** make it a blocking CI gate at that moment — first observe, in one CI run, whether it fires `IL3058` against AWS/Serilog dependencies outside AlexaVoxCraft's control; if it does, downgrade it to a non-blocking warning (or scope it only to `AlexaVoxCraft.Model`/`AlexaVoxCraft.Model.Apl`, which have no such third-party runtime dependencies at all per §5/§6 below, and can safely be a hard gate immediately) until the noisy dependencies themselves ship AOT-compatible releases. This reinforces, rather than replaces, the core validation bar below: **a clean `VerifyReferenceAotCompatibility`/analyzer run is necessary but not sufficient — the only real bar is steps 1-5 above: an actual published native binary that executes correctly against representative fixtures.** Sources: [Prepare .NET libraries for trimming](https://learn.microsoft.com/en-us/dotnet/core/deploying/trimming/prepare-libraries-for-trimming) (`VerifyReferenceTrimCompatibility`/`IL2125` — the trimming-side sibling of the AOT-side property, confirming the mechanism), MSBuild/analyzer documentation for `VerifyReferenceAotCompatibility`/`IL3058`; [.NET 10 runtime now available in AWS Lambda](https://aws.amazon.com/blogs/compute/net-10-runtime-now-available-in-aws-lambda/); [Compile .NET Lambda function code to a native runtime format](https://docs.aws.amazon.com/lambda/latest/dg/dotnet-native-aot.html).

## 12. Architectural alternatives

**A. Status quo, documented as JIT-only (no code change).** Add explicit documentation stating Native AOT is unsupported, and that `PublishTrimmed`/`PublishAot` consumers should expect runtime failures. AOT correctness: none — doesn't satisfy the product requirement at all. Included only as the baseline against which cost/benefit of the others should be judged. Zero implementation complexity, zero risk, zero benefit toward the stated goal.

**B. Library-owned `JsonSerializerContext` per package (`Model`, `Model.Apl`, `Model.InSkillPurchasing`, and — per the corrected scope in §9 — `Smapi`), `AlexaTypeResolver`/`BaseClient`'s defaults rebuilt on top of them as the new default, consumer resolver-chain extension point added (the recommended direction, detailed in §13).** AOT correctness: high, once validated per §11 — this directly targets the one dominant blocker (`DefaultJsonTypeInfoResolver`) without touching the already-AOT-legitimate converter/discriminator design. Trimming correctness: high, same reasoning. Public API impact: one additive method (`AlexaJsonOptions.RegisterTypeInfoResolver`/`RegisterContext<T>`); no breaking changes to existing signatures. Consumer ergonomics: unchanged for existing JIT consumers; AOT consumers with only built-in types need zero new code; AOT consumers with custom `JsonAttributeBag`/`BaseClient` types need one new `JsonSerializerContext` + one registration call. Backward compatibility: high (§10). Implementation complexity: moderate — mechanical work generating `[JsonSerializable]` declarations for every closed-hierarchy type (potentially 150+ types across Model + Model.Apl), but conceptually simple; the risk is almost entirely in careful migration/validation (§11), not design. Source-gen requirement: yes, this alternative *is* the source-gen adoption. Extensibility: preserves exactly the extensibility that exists today (nothing more, nothing less — consumers can't extend `Request`/`Directive`/APL-component hierarchies today, and this alternative doesn't change that). Performance: source-gen `JsonTypeInfo` resolution is faster than reflection-based resolution in the general case, a secondary benefit. Testing complexity: moderate, largely covered by reusing existing Verify snapshots (§11). Long-term maintenance: every new model type must be added to a `[JsonSerializable]` list — a discoverable, compile-error-if-forgotten failure mode (a type used but not declared in the context produces a clear STJ error, not a silent gap) if done via a generator-emitted list rather than hand-maintained. No new magic: the resolver-chain composition is exactly the pattern Microsoft documents for this scenario (§6), not a bespoke mechanism.

**C. Keep `DefaultJsonTypeInfoResolver` as-is, but wrap every call site in `[RequiresDynamicCode]`/`[RequiresUnreferencedCode]` and ship an explicit "AlexaVoxCraft does not support Native AOT" stance with these annotations propagated through the public API so consumers get a build-time warning instead of a silent runtime failure.** AOT correctness: still doesn't satisfy the product requirement (nothing becomes AOT-*compatible*; this only improves the failure mode from "confusing runtime exception" to "clear build warning"). Explicitly disallowed by the brief's constraints ("do not introduce preservation attributes or linker descriptors merely to silence warnings" — this alternative is the mirror image, propagating warnings rather than silencing them, but shares the same flaw of treating the symptom rather than the architecture). Included for completeness because it's a real, low-effort thing a team could do short of full AOT support, and is arguably a reasonable *interim* step while B is implemented, but should not be the end state.

**E. Gated JIT-reflection-fallback compatibility path, layered on top of B.** AOT publish path = generated contexts only, required, no reflection anywhere (identical to B). JIT/non-AOT path = generated AlexaVoxCraft metadata plus an *optional* reflection fallback for unknown consumer types, written in the case-(3) shape confirmed correct in §6: `TypeInfoResolver = JsonTypeInfoResolver.Combine(ModelContext.Default, ...) .WithAddedModifier(...)` as the base, with a final fallback member of the chain constructed as `JsonSerializer.IsReflectionEnabledByDefault ? new DefaultJsonTypeInfoResolver() : null` (omitted/no-op when `null`/reflection disabled). Concretely, this would let `JsonAttributeBag.Set<MyGameState>(...)`/`Get<MyGameState>(...)` (`JsonAttributeBag.cs:44,54`) keep working today, with **zero new registration**, for any JIT consumer who has never heard of `JsonSerializerContext` — matching the library's current, zero-ceremony ergonomics exactly — while a Native AOT consumer hitting the same call for an unregistered `MyGameState` gets a clear, immediate `InvalidOperationException`/`NotSupportedException` (STJ's own message when no resolver in the chain can produce `JsonTypeInfo` for a type) rather than a confusing failure, and *must* register their own generated context via `RegisterTypeInfoResolver` to fix it. **Verified against §6's findings, precisely**: because the fallback member is constructed via the `IsReflectionEnabledByDefault ? ... : null` ternary — the exact pattern §6 confirmed the linker treats as a link-time constant and removes entirely — this does **not** root `DefaultJsonTypeInfoResolver`'s reflection code in a `PublishAot` build; the AOT-compiled binary contains zero unreachable reflection IL, `EnableAotAnalyzer` output stays clean, and only the JIT-published binary carries the reflection fallback. **Preserves current JIT behavior exactly**: `IsReflectionEnabledByDefault` defaults to `true` on ordinary (non-`PublishTrimmed`/non-`PublishAot`) JIT publishes, so the fallback is present by default for exactly the consumers who rely on it today, with no opt-in step. **Resolver-chain ordering guarantees library-generated metadata wins over reflection when both could apply**: `JsonTypeInfoResolver.Combine`/chain resolution queries resolvers in declared order and returns the first non-null `JsonTypeInfo` (§6/§7), so placing the reflection fallback *last* in the chain (after the library's own generated context(s) and after any consumer-registered context) guarantees it is only ever consulted for types none of the generated metadata covers — it can never silently shadow or diverge from the library's own generated shape for `Model`/`Model.Apl`/ISP types. **Public API stays intuitive**: no new required call for existing JIT consumers; the one new method (`RegisterTypeInfoResolver`) is opt-in and only needed by AOT consumers or JIT consumers who want to eliminate reflection early. **Weighed against B**: this is not a competing architecture, it's B *plus* a JIT convenience tail — it costs one small, well-precedented conditional resolver construction inside `CreateOptions()` and a short doc note ("reflection fallback only applies outside Native AOT publishes"), in exchange for a materially softer migration story for the large population of existing JIT-only skill authors who will never publish AOT and would otherwise see zero behavior change anyway (since B alone, without a chain-appended consumer context, already fails for their custom `JsonAttributeBag` types the moment `AlexaTypeResolver`'s reflection is replaced with a closed generated context — this is the one real behavioral gap B introduces that E closes for free). **Verdict — CONFIRMED, not merely weighed.** This research pass settles Alternative E as part of the recommended architecture (§13 step 3), not as an open alternative still being weighed: the goal is zero *unsupported* reflection on the Native AOT path plus backward-compatible ergonomics on the JIT path — not zero reflection everywhere as an end in itself. Reflection that is (a) gated behind `JsonSerializer.IsReflectionEnabledByDefault` and (b) proven, per §6's precise link-time-constant analysis, to compile out of the Native AOT output entirely (not merely be unreachable at runtime, but *absent* from the published binary, with no `EnableAotAnalyzer` warning) is acceptable and intentional, not a compromise. It is presented here as "Alternative E" only for narrative continuity with the rest of §12's alternative set — every other section of this document (§1, §13) treats it as settled.

**D. Full closed-world redesign: remove or restrict the open-`T` surfaces (`JsonAttributeBag.Get<T>`/`Set<T>`, `BaseClient.Deserialize<TResult>`) to require an explicit `JsonTypeInfo<T>`/`JsonSerializerContext` argument at every call site, eliminating the shared static `AlexaJsonOptions.DefaultOptions` singleton entirely in favor of per-call, explicitly-supplied type metadata.** AOT correctness: highest possible (nothing is ever ambient/implicit). Public API impact: **breaking** — every `Get<T>(key)` call in every existing consumer skill becomes `Get<T>(key, MyContext.Default.MyType)` or similar; this is a significant, disruptive change to a widely-used, already-shipped API (`JsonAttributeBag` per MEMORY.md was itself a recent breaking refactor — a second breaking change to the same surface in short order carries real consumer-trust cost). Consumer ergonomics: markedly worse for the common case (most consumers don't need per-call type metadata; a startup-time registration, as in B, covers the same correctness guarantee with far less ceremony). Explicitly the kind of "optimize only for AOT users at ordinary-consumer expense" the brief warns against avoiding. Not recommended, but named because the brief requires a credible alternative set, not just the recommended one dressed up as several options.

## 13. Recommended direction

**Alternative B, extended with Alternative E's gated JIT-reflection tail** (§12), i.e.:

1. Introduce one internal, `[JsonSerializable]`-annotated `JsonSerializerContext` per package that owns closed model types — `AlexaVoxCraft.Model` (base `Request`/`Directive`/`Card`/`OutputSpeech`/etc.), `AlexaVoxCraft.Model.Apl` (APL component/command/document/data-source types), `AlexaVoxCraft.Model.InSkillPurchasing` (ISP models) — covering every type reachable from the existing closed discriminator tables (`RequestConverter`'s resolvers, every `BasePolymorphicConverter<T>` subclass's `DerivedTypes`, `APLComponentConverter`'s dictionary, and siblings) plus every plain (non-polymorphic) model type referenced from those. This granularity and internal visibility is not a preference — it's what the actual `ProjectReference` graph requires and permits (§7's "Context granularity and visibility" subsection): `Model` cannot see `Model.Apl` types, and no consumer needs to see any of these classes directly, only the `IJsonTypeInfoResolver` instances they produce.
2. Rebuild `AlexaTypeResolver`/`AlexaJsonOptions.CreateOptions()` so the default `TypeInfoResolver` is built as `JsonTypeInfoResolver.Combine(ModelContext.Default, ...consumer/APL/ISP-registered resolvers...)`, with the existing `ShouldSerialize` conditional-property logic and every `RegisterTypeModifier<T>` registration re-expressed via repeated `JsonTypeInfoResolver.WithAddedModifier(...)` calls applied to the *outermost* combined resolver (§6/§7 — proven, not assumed, to preserve today's "one global modifier list, filtered by `ti.Type == typeof(T)`" semantics exactly, including today's already-correct support for registering modifiers after `DefaultOptions` has been read once).
3. **Append a gated JIT-only reflection fallback as the last member of that chain** (Alternative E, §12): `JsonSerializer.IsReflectionEnabledByDefault ? new DefaultJsonTypeInfoResolver() : null`, filtered out when null. This preserves today's zero-registration ergonomics for `JsonAttributeBag.Get<T>/Set<T>` and `BaseClient.Deserialize<TResult>` on any JIT-only skill (the overwhelming majority of today's consumer base) with no code change required of them, while the `IsReflectionEnabledByDefault` link-time-constant behavior (§6) guarantees this fallback is compiled out entirely — not merely unreachable, but absent — from any `PublishAot` build, so it cannot silently mask an AOT consumer's missing registration.
4. `AlexaVoxCraft.Model.Apl`'s existing `AplSupport.Add()` bootstrap (`APLSupport.cs:14-134`) gains one additional call, `AlexaJsonOptions.RegisterTypeInfoResolver(AplModelContext.Default)`, alongside its existing `RegisterTypeInfo<T>()`/discriminator-registration calls — no new bootstrap mechanism, reusing the one call site consumers already must make today for APL support. `AlexaVoxCraft.Model.InSkillPurchasing`'s existing `InSkillPurchasingSupport.Add()` (`InSkillPurchasingSupport.cs:15-19` — this already exists, correcting the prior pass's assumption that it would need to be newly created) gains the identical one line. No new bootstrap method is invented for either package, and none should be for `Http`/`InSkillPurchasing`(runtime)/`Smapi` either (step 9) — each rides its package-owned resolver in on whatever existing constructor/DI-registration path it already has (§7).
5. Preserve `AlexaJsonOptions.RegisterConverter<T>`/`RegisterTypeModifier<T>` exactly as-is (proven to compose correctly regardless of the base resolver, §6/§7); add exactly one new public method, `AlexaJsonOptions.RegisterTypeInfoResolver(IJsonTypeInfoResolver)` (or an equivalent `RegisterContext<TContext>()` convenience overload), so consumers with custom `JsonAttributeBag`/`BaseClient` types, or a custom `IDirective`/`IRequestTypeResolver` registered via the existing `RegisterDirectiveDerivedType<T>`/`RegisterRequestTypeResolver<T>` extension points (§7/§8), can append their own generated context to the chain with one call at startup — the same idiom `AplSupport.Add()` already teaches them.
6. Do **not** rewrite any of the existing custom polymorphic converters (`RequestConverter`, `BasePolymorphicConverter<T>` subclasses, `APLComponentConverter`, etc.) or migrate to `[JsonPolymorphic]`/`[JsonDerivedType]` — they are already AOT-legitimate by shape (§6, §8) and rewriting them adds wire-format risk for no compatibility benefit.
7. **Eliminate the `APLValueConverterFactory`/`APLValueCollectionConverterFactory` `MakeGenericType` hazard by rewriting the two factories' internals to a closed dispatch table, not by scattering per-property registrations or building a second source generator (§8's three-design comparison, revised from the prior pass).** §8's exhaustive enumeration found 48 closed `APLValue<T>` and 30 closed `APLValueCollection<T>` instantiations, all package-owned — **but the fix location is the two factory classes themselves, not the ~90 model files that use them.** Replace `APLValueConverterFactory.CreateConverterInternal` (`APLValueConverterFactory.cs:210-244`) and `APLValueCollectionConverterFactory.CreateConverter` (`APLValueCollectionConverterFactory.cs:18-28`)'s `Activator.CreateInstance(typeof(APLValueConverter<>).MakeGenericType(valueType), ...)` calls with a closed dispatch (an `if (valueType == typeof(X)) return new APLValueConverter<X>();` chain, or a `Dictionary<Type, Func<JsonConverter>>` built once — the same shape the file already uses today for its `APLValue<object>` special case, `APLValueConverterFactory.cs:186-221`), covering all 48/30 closed types. **Zero changes to any `RegisterTypeInfo<T>()` method or any of the ~90 model files are required** — the factories keep their existing `JsonConverterFactory` shape and existing `[JsonConverter(typeof(...Factory))]` attribute placement on the open generic type definitions (`APLValue_T.cs:9`, `APLValueCollection_T.cs:17`), so STJ continues to invoke them automatically for every property without any per-property wiring. **Pre-condition, sequenced first**: fix the `System.ComponentModel.Component`/`APLComponent` defect (`AlexaSwipeToAction.cs:179`, `AlexaTextListItem.cs:28`, §8, §14) *before* enumerating the final closed-type list this dispatch table is built from, so the table encodes the intended type universe, not the accidental one. The confirmed-unreachable `APLEnumerableValueConverter<TValue,TList>` branch (§5, §8) is dropped from the closed table and kept only as a narrow, `[RequiresDynamicCode]`/`[RequiresUnreferencedCode]`-annotated fallback arm gated behind `JsonSerializer.IsReflectionEnabledByDefault` (§6 item 3, §13 step 3) for a consumer who declares an `APLValue<T>`/`APLValueCollection<T>` instantiation outside the library's own object graph — never reachable under `PublishAot`. This requires no new source generator (§8's comparison rejects both the per-property-registration design and a generated version of the same table, on maintainability grounds, not merely AOT-safety) — it is a self-contained rewrite of exactly two files.
8. **Separately address the non-JSON `SkillMediator.Send` reflection dispatch (§5) — as a hard gate on the "Native AOT compatible" claim, not an optional follow-on.** Likely fix: have the MediatR source generator (which already exists and already knows every registered `IRequestHandler<T>` at compile time) additionally emit a compile-time switch/dictionary from `Type` to a non-reflective wrapper-factory delegate, eliminating `MakeGenericType`/`Activator.CreateInstance` the same way it already eliminated reflection from DI registration. This is the one place in this redesign where extending the existing MediatR generator genuinely is the right tool — a distinction worth preserving precisely, since step 7 is a case where it is *not* the right tool. **Sequencing**: this may ship in the same release as the JSON work or as a separately staged PR/workstream — that scheduling choice is free — but it may **not** ship *after* a release that is publicly labeled "Native AOT compatible," because Native AOT compatibility is a product-level, end-to-end capability claim (does the consumer's skill run under `PublishAot`?), not a JSON-only claim; a release cannot honestly carry that label while `SkillMediator.Send`'s dispatch path is unverified or still reflective. §11's validation strategy (real `PublishAot` binary, actually executed, exercising real handler dispatch) is the concrete gate this must pass before the label is used.
9. **Bring `AlexaVoxCraft.Http`, `AlexaVoxCraft.InSkillPurchasing`, and `AlexaVoxCraft.Smapi` all into scope** (§9, corrected from the prior pass's "defer Smapi" conclusion): per product-owner clarification, SMAPI clients are used from Lambda functions in real published-package consumers, not merely at build/deploy time, so `Smapi` cannot be excluded from the runtime-AOT claim just because this repo's own internal `ProjectReference` graph shows no in-repo consumer. `Http` remains in scope for the reason already established (a genuine runtime dependency via `AlexaVoxCraft.InSkillPurchasing`'s live, mid-request ISP API calls). Concretely: `BaseClient`'s orphaned default `JsonSerializerOptions` (`BaseClient.cs:36-44`) and `Smapi`'s three independent ad hoc options instances (`AlexaSkillInvocationClient.cs:20-28`, `AlexaInteractionModelClient.cs:17-18` via `BaseClient`'s default, `InteractionModelBuilder.cs:177-190`) all need the same context/chain treatment — a `Smapi`-owned closed context for `InteractionModelDefinition` and friends, plus the same consumer-resolver-chain contract as `JsonAttributeBag` for `AlexaSkillInvocationClient.InvokeAsync<TRequest,TResponse>`'s open-`T` surface (§9). None of `Http`/`InSkillPurchasing`/`Smapi` needs a new public bootstrap method for this (§7) — each wires into its existing constructor default or existing `AddInSkillPurchasing()`/`AddSmapiDeveloperClient()`/`AddSkillInvocationClient()` DI extension.
10. Only after §11's validation strategy (including the `VerifyReferenceAotCompatibility` guidance added in this pass) passes reliably in CI should `IsTrimmable`/`IsAotCompatible` be set on the affected packages (§9) — remembering that `IsAotCompatible=true` transitively sets `IsTrimmable`/`EnableTrimAnalyzer`/`EnableSingleFileAnalyzer`/`EnableAotAnalyzer` (§11), so a clean analyzer run at that point is a floor, not the finish line: the finish line is still "a published native binary executes correctly against representative fixtures" (§11 steps 1-5).

This satisfies "smallest architecture that fully satisfies the requirement" (one new method, no converter rewrites, no `[JsonPolymorphic]` migration, no new source generator for the APL factory hazard), "protect long-term public API quality" and "minimize breaking changes" (§10, §12-B), "prefer compile-time/source-generated solutions" (directly, while still keeping a deliberately-gated, non-rooting reflection convenience for JIT consumers, §12-E), and "any public API introduced for AOT should feel natural for normal non-AOT consumers too" (the new registration method mirrors `RegisterConverter`/`RegisterTypeModifier`, which non-AOT consumers already use, and JIT consumers see zero behavior change at all thanks to step 3).

## 14. Open questions

Several items are resolved as of this refinement pass and are removed from the open-questions list accordingly:
- `AlexaVoxCraft.Http`/`AlexaVoxCraft.InSkillPurchasing`/`AlexaVoxCraft.Smapi` scope (§9 — all three are now in scope, per explicit product-owner clarification that SMAPI clients are also used from Lambda functions in real applications; none is deferred as tooling-only).

- The APL converter-factory remediation design (§8, §13 step 7 — settled on centralized closed dispatch inside the two existing factory classes, not per-property scattering and not a new source generator).
- The full `APLValue<T>`/`APLValueCollection<T>` instantiation set (§8 — exhaustively enumerated: 48 + 30 closed instantiations, plus one `System.ComponentModel.Component` defect, now sequenced as a pre-migration bugfix rather than left open, §8/§13 step 7).

- `RegisterRequestTypeResolver<T>`'s documentation treatment (§7/§8 — settled as: keep it technically supported under the same AOT contract as `RegisterDirectiveDerivedType<T>`, but do **not** promote its documentation prominence merely because the AOT work touches it; its lack of a confirmed external caller and lack of XML docs is a separate, pre-existing product/API-surface fact this research doesn't change and isn't recommending a change to).
- `[JsonPolymorphic]`/`[JsonDerivedType]` as a future direction (§8 — settled OUT OF SCOPE: considered, rejected, no evidence-based user need; not left open as a positioning question).
- The gated JIT-reflection fallback (§12 Alternative E, §13 step 3 — settled as CONFIRMED, part of the recommended architecture, not an open alternative still being weighed; see §12's revised verdict).
- Whether the mediator-dispatch fix (§13 step 8) can ship as a separate PR/workstream from the JSON work — yes, scheduling is free, but it is now a **hard gate** on ever using the "Native AOT compatible" label, settled in §1/§13 step 8, not a scheduling question left open.

Genuinely unresolved, requiring the user's/team's input rather than more research:

- **Does AWS's `provided.al2023` custom runtime + `Amazon.Lambda.RuntimeSupport` impose any additional AOT constraints beyond what's captured in §6/§11?** This pass confirmed AWS has actively updated its .NET Lambda tooling for Native AOT (via the `.NET 10 runtime now available in AWS Lambda` post and the `dotnet-native-aot` deployment guide) but did not independently confirm whether the specific `Amazon.Lambda.RuntimeSupport`/`Amazon.Lambda.Serialization.SystemTextJson`/`Amazon.Lambda.Core` package *versions* this repo pins carry `IsAotCompatible=true` assembly metadata — §11's newly-added `VerifyReferenceAotCompatibility` guidance is the mechanism to answer this empirically once `IsAotCompatible=true` is set on `AlexaVoxCraft.MediatR.Lambda`, but that hasn't been run yet.
- **Serilog/`LayeredCraft.Logging.CompactJsonFormatter`'s AOT-compatibility status** (dependencies of `AlexaVoxCraft.MediatR.Lambda`, §11): not independently verified in this pass; Serilog's ecosystem has historically leaned on reflection-based sinks/enrichers. Whether these specific packages are AOT-clean, and whether that materially affects the CI-gate decision in §11, is unresolved and empirically answerable the same way as the AWS packages above.
- **`AlexaVoxCraft.Observability` and `AlexaVoxCraft.MinimalLambda` were not deeply audited in this pass** (§9) and should be separately verified for their own JSON/reflection surfaces before being included in the "AOT-compatible" package set.
- **Exact placement of the SMAPI/ISP request/response types in the invocation-testing surface** (`AlexaSkillInvocationClient.InvokeAsync<TRequest,TResponse>`, §9): confirmed structurally to need the same open-`T` consumer-resolver-chain contract as `JsonAttributeBag`, but whether real-world consumers of this API are themselves AlexaVoxCraft-owned `SkillRequest`/`SkillResponse` types (in which case the existing `Model` context already covers them and no extra consumer action is needed) or fully custom types (requiring a consumer-supplied context) was not independently confirmed — this affects how prominently the open-`T` caveat needs to be documented for this specific API versus treated as a rare edge case.
